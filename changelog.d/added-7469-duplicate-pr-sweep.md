- Added `duplicate_sweep`, a periodic cross-PR pass that clusters open PRs by changed-file set and suggests which one to keep ([#7469](https://github.com/hivecommons/hive/issues/7469)). Until now nothing in hive could see two PRs at once: `ApplyDuplicatePRGuard` only runs at PR-open time and only for hive's own agents, so a duplicate that already exists between two PRs was invisible — on a 423-PR queue with no auto-merge, the one lever that could actually shrink it. The sweep posts an idempotent suggestion on the later PRs naming the survivor and the shared files, or, for a bot regenerating the same artifact daily, one summary on the newest PR rather than one comment per PR. It is graded: identical changed files *and* byte-identical patches is the strong tier, matching files with differing patches is explicitly the weak one, and the comment says which it is. **The output is a suggestion and never an action** — changed-file identity is a candidate generator whose false positives (three dependency bumps sharing one manifest, three unrelated fixes to one busy file) are indistinguishable from true positives at this layer, so nothing here closes, labels, approves or merges, and the comment says so. Two separate opt-ins, both off by default: `duplicate_sweep.enabled` turns on a report-only pass an operator can read in the log, and `duplicate_sweep.post_comments` is the separate grant that lets it write. The review swarm gains no permission from any of this — the write is the hive's own App token on the existing canary-gated, mention-neutralized, secret-scrubbed comment path.
