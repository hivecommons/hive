- Three more automated paths leave an issue alone while it has an open GitHub sub-issue. An issue whose remaining work was moved into sub-issues is not done while one of them is open, but three paths closed it as completed without looking. (1) When a pull request is closed as already landed, each issue its body names with a closing keyword was closed and given a "this issue is done" note; an issue with an open sub-issue is now left open with no note. (2) Question auto-close closed an answered question at the end of its window; with an open sub-issue the schedule now ends as `open_sub_issues`, nothing is written on the issue, and that answer is not scheduled again. (3) An agent's `hive-open-issue close` request closed any issue the agent may write to; for an issue with an open sub-issue the request is now refused, parked as `.denied` with the reason in its result and never retried, and `--override-reason` does not change that. In all three the issue stays open until the issue stage sweep closes it once every sub-issue is closed, or a person closes it. Only native GitHub sub-issues count, read from the `sub_issues_summary` block on the issue: the first two paths take it from the issue read they already made, so they add no request, and the agent's close request makes one extra read of the issue before anything is written, retried like any other failed read. An issue with no sub-issues or with all of them closed, and a pull request, are handled exactly as before.
