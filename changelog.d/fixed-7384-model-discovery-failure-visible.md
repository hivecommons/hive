- A failed CLI model discovery is no longer silent, and auto-heal can no longer act on it ([#7384](https://github.com/hivecommons/hive/issues/7384)). On the projectbluefin spoke the Copilot SDK helper failed on arm64 (#7365), discovery fell through to the raw-HTTP chat-completions catalog — a *live* list that is not the one the Copilot CLI uses — the dropdown rendered it as authoritative, and the dashboard's model auto-heal moved all six agents onto `gpt-4o-mini-2024-07-18` off it; nothing recorded a problem for two days. Now: (1) the audit log gains a `system` entry `model_discovery_failed` — backend, platform (os/arch), whether a fallback or a degraded list is served, and the probe's own error text — when discovery breaks, and `model_discovery_recovered` when it heals, once per transition rather than per 30 s probe; (2) `/api/config/backends` carries `degraded` and `discovery: {ok:false, error}` and the model dropdown labels every entry `⚠ model discovery failed — showing fallback list` (or `… degraded — not the CLI catalog`) with the error as the tooltip, instead of a static list that looks like a real catalog; (3) a list that is not a clean live probe — static fallback *or* degraded — is never authority: the dashboard auto-heal skips it, model validation treats it as unverifiable, and it is kept out of the live-list retention. Not-configured fallbacks (no credential, no helper installed) are unchanged and unaudited: they are not failures.
