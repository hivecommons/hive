- The contributor image now carries a small repository-check baseline, so a container-mode agent can run the checked-out repository's own checks instead of a substitute for them ([#7925](https://github.com/hivecommons/hive/issues/7925)). The image could run the relay and the agent CLIs but shipped no `pip`, `pytest`, `pyyaml`, `jsonschema`, `requests`, `make`, `just`, `shellcheck` or `yq` — so an agent could edit a Python-, Make- or `just`-driven repository and then not run its test suite, its `just check`, or its `make ci`. That is a correctness problem rather than a convenience one, because an agent that cannot run the real check reaches for a proxy that looks green: on one task, pytest-style tests run under `python3 -m unittest` reported `Ran 0 tests ... OK` and were about to be cited as a passing run. `just` and `yq` are not packaged in Debian 12 and are installed the way the image already installs Go, muse and omp — a pinned release verified with `sha256sum` before install, never a curl-pipe-to-shell installer; `JUST_VERSION` matches the pin CI already uses. Because Debian marks its system Python externally-managed and the container runs as the unprivileged `dev` user, Python packages install into `/opt/hive/pyenv`, a `--system-site-packages` virtualenv owned by `dev` and first on `PATH`, so `pip install` works inside a task with no privilege and no flags. Container tooling (`podman`, `skopeo`, `buildah`, `crane`) is deliberately still absent: it needs privileges the contributor container should not hold.
