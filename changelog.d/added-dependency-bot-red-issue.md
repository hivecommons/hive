- New opt-in `auto_merge.dependency_bot_red_issue.enabled` (default off; Settings → Features → Auto-merge, admin MCP `auto_merge.update` field `dependency_bot_red_issue_enabled`). When the dependency-bot sweep's red-CI hand-off fires for a Renovate, Dependabot or mergeraptor PR that adoption did not take, the sweep files one issue in that repository asking for the companion change the bump needs, but only on evidence that this bump is at fault: within one check suite of the head a failing attempt started after an earlier failing attempt had finished (or the hive's transient re-run failed again) and the check never passed on it, no other open PR fails the same checks and no open `[shared-ci]` incident names them, the failing runs left failure-level error annotations beyond the exit code, and every failing required check's newest run on the base tip the head already contains concluded success after the failure started. The issue links the PR and its failing runs, quotes the errors, asks for a repository fix instead of an edit to the bot's branch, and says what then has to happen on the PR for that bot. One issue per PR and failing check set, found again by a first-line body marker the hive itself wrote, through the `issue_file` write-back gate (checked before any read); at most 3 PRs are checked per pass and no hand-off ever waits for the filer. The hand-off and its `needs-human` label are unchanged apart from a line naming the issue, and the hive posts one note on the issue when the PR merges, closes or goes green, without ever closing it.
