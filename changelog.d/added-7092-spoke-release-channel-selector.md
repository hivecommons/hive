- A hosted spoke's own dashboard can now select the release channel it follows ([#7092](https://github.com/hivecommons/hive/issues/7092)). Channel switching already existed, but only as an admin control on the *hub* dashboard, so an operator looking at their own spoke saw the channel it was on (added alongside the last-upgrade-outcome panel) with no way to change it — one of three "lost in version space" complaints, next to a version that read a bare `v4` until builds began stamping `git describe`. The selector posts to a new `/api/release-channel` on the spoke, which relays to the hub's existing `switch-branch` endpoint rather than adding a second delivery path: that endpoint keeps ownership of validating the channel maps to a real image tag and of confirming the tag is actually published on GHCR, the check that catches a deprecated branch whose well-formed `<branch>-latest` tag CI no longer builds — a pull that fails with `manifest unknown` while Kubernetes keeps the old ReplicaSet serving, leaving the hive looking alive on stale code. Because the hub records the choice as intent (`tracked_channel`) and re-arms delivery on every heartbeat whenever the spoke's *reported* image tag disagrees with it, a selection survives a hub restart mid-switch and self-heals an upgrade that overwrote the channel tag; the dashboard shows the channel as **pending** until the Deployment image actually lands, since intent and the reported ref legitimately disagree while a switch is on the wire, and renders an honest "unknown" — with the observed tag — for a spoke tracking a branch tag or a pin instead of offering a control that would silently do nothing. Authorization is bound to the caller's own hive: the spoke's dashboard-token proof is verified against the hive ID in the request path and the resolved user must still be that hive's owner, so a spoke holding its own token cannot retarget a different hive (covered by a test that fails with `status = 200, want 401` if the binding is removed).
