- A merged PR no longer gets an issue that has open sub-issues told it is fixed, marked likely-done or closed by the hive. Two paths did that. Close-on-merge posted `Fixed by #N (merged …). Closing.` and closed the issue (or, for an issue behind a confirmation gate, posted the awaiting-confirmation comment and added `hive/likely-done`) for any merged PR that named the issue with a closing keyword, and the issue stage sweep posted its own `Fixed by #N (merged). Closing because Hive's PR claim metadata says this PR was the full fix.` and closed it for a merged hive-authored PR whose claim is closing; neither looked at the issue's sub-issues, so a parent whose remaining work had been moved into three open sub-issues was commented on and closed with all three open. In close-on-merge the comment goes out before the close and carries the already-handled marker, so the note would have stayed even if only the close had been refused. Now both paths write nothing on an issue with an open sub-issue: no comment, no label, no close. Close-on-merge reports `skipped` with the new reason `open_sub_issues`, logs one INFO line (repo, issue, PR, open and total sub-issues) and settles the claim like its other skips, so the ledger sweep looks again once per `issues.close_on_merge_recheck`; the stage sweep drops the merged claim and leaves the parent at its unclaimed stage, never stalled, saying so once at INFO and at DEBUG on later passes. Neither path makes a new GitHub request: close-on-merge reads GitHub's `sub_issues_summary` off the issue payload it already fetches (its single issue read, or the open-issue listing a sweep works from, which now keeps that block and is the same request the enumeration makes), and the stage sweep uses the sub-issue count already on the enumeration row. The parent closes through the existing decomposed-parent sweep once every sub-issue is closed. An issue with no sub-issues, or with every sub-issue closed, is commented on, labelled and closed exactly as before; tracking issues, reopened issues, reporter confirmation, partial coverage (`hive/partially-addressed`, the partial-work note) and `issue_marked_open` are unchanged. GitHub itself still closes an issue when a PR with a closing keyword merges to the default branch; the hive cannot prevent that.
