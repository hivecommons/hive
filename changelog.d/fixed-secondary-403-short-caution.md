- One GitHub secondary-limit 403 no longer stalls merges for over an hour. A secondary 403 with no `Retry-After` used to assume a full hour, then add the 10-minute slow-start window. For those 70 minutes every low-priority call that would queue more than 5s was shed, including the automerge sweep's commit-status read. On the projectbluefin hive (2026-10-28) one search refusal after a restart meant no PR merged for over an hour, even an approved PR with 19/19 checks green, while the primary quota stood at 87%. Such a 403 now backs off for `Retry-After` when GitHub sends it, or until `X-RateLimit-Reset` when `X-RateLimit-Remaining` is `0`. Otherwise it waits one minute, GitHub's documented rule, and doubles on each repeat up to 15 minutes. Separately, once an automerge lane reaches a candidate PR, the PR's evaluation and merge run at normal pacing priority, so its status and check-run reads are never shed as housekeeping.
