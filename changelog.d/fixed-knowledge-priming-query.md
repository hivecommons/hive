- **Primed knowledge is now about the task, not about the hive's own routing.** The "# Relevant Knowledge" search built its query from an issue's labels, complexity tier and title words. On hive-routed work those were mostly the hive's own: `epic`, `approved-direction`, `stage/010-actionable`, `agent/reviewer`, `medium`, and the `[reviewer] Review backlog (style):` title stem. They match review and planning notes in every repo, so a scanner task on `projectbluefin/utah-packages#879` was primed with entries about other repos, and on the projectbluefin hive the reviewer, quality and sec-check kicks carried the same section whatever their work. The query now leaves out what the hive itself put on the item: its routing label families (`stage/`, `agent/`, `origin/`, `hive/`, `hive:`, `hive-pause/`, `author/`, `triage/`, `size/`, `lifecycle/`, `do-not-merge/`, `needs-`, `dco-signoff`, `sentinel-`, plus `approved-direction`, `hive-review`, `lgtm`, `approved`, `claimed` and `epic`), the complexity tier, a leading `[<agent>]` tag when it names a hive lane, origin source or configured agent (a person's `[nvidia] …` keeps `nvidia`), and the review backlog stem, cut down to its perspective (`style`, `security`). When nothing is left, the query falls back to the one earlier releases built, so no kick loses its knowledge section. The task's repository now counts too: within a type, an entry tagged `repo:<org>/<name>` for the repo being worked on (or `repo:<name>`, as a code map configured by path is tagged) ranks ahead of an otherwise equal entry about another repo. The tag only orders entries the search already found and never adds one, and the confidence a kick shows is unchanged. This applies to resident kicks and to contributor role guidance alike.
