- A head that GitHub's merge queue removes with `failed_checks` is no longer queued again every 30 minutes forever when neither the head nor the base moved. The 30-minute retry is kept for a flaky merge-group check, but each head gets it once per base tip, in every lane that queues a PR (the label-queued lane included): after a second `failed_checks` rejection of the same head on the same base tip, the PR moves to `stage/085-needs-decision` with `native-merge-queue-rejected-repeatedly`, and its comment links the repository's merge-group runs. Nobody has to queue it again by hand: the hive retries the same head on its own 2 hours after the second failure and then every 6 hours (about four merge-group runs a day instead of forty-eight), so a cause fixed somewhere else, such as a dependency rebuilt in another repository, is picked up without a person. The dashboard's 085 row offers **Retry now (the cause is fixed)**, which approves the head so the next pass queues it again; a `/hive decision approve` comment does the same (a plain approving review on GitHub does not), and a push retries at once too. Before, such a PR bought a full merge-group CI run every 30 to 40 minutes while it sat at `stage/100-merge-queue` looking healthy. The base tip comes from the compare the self-authored, trusted-author and contributor lanes already run for a rejected head, so they make no extra GitHub call; the label-queued lane makes one REST compare per pass while it holds such a rejection. There is no new setting. Entries other actors queue (a person, a Prow or Tide merge bot) are not bounded by this.
