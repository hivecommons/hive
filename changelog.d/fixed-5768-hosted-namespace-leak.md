- Hosted-spoke provisioning no longer leaks its Kubernetes namespace when the manifest apply fails, and fleet health now reports `hive-hosted-*` namespaces that no hive record accounts for ([#5768](https://github.com/kubestellar/hive/issues/5768)). A console canary found 76 stuck pods — 64 Unschedulable and 12 Pending on unbound PVCs — spread across dozens of leaked `hive-hosted-hosted-*` namespaces on one CI cluster, quietly holding quota and PVCs on a shared cluster and polluting every health surface that reads pod issues. Two things let that accumulate: `kubectl apply` creates the Namespace first and rolls nothing back when a later object in the same manifest is rejected, so a failed provision left the namespace behind with no owner; and every hub-side sweep derives its namespace list *from* the hive registry, so a namespace with no registry entry was invisible by construction. Provisioning now records whether the namespace existed immediately before the apply and deletes it on failure only when it did not — a pre-existing or undeterminable namespace is deliberately left alone, since that delete would cascade to a live spoke's pods and PVCs. Separately, each per-cluster health entry gains `leaked_namespaces`, listing unaccounted-for hosted namespaces older than six hours, oldest first, with the hive-id label when one was stamped; the report is strictly read-only and deletes nothing, and it reports *unknown* rather than a reassuring zero when the cluster is unreachable or the hive registry reads as empty (which is indistinguishable from an unreadable one). A janitor that reclaims the namespaces this now surfaces is deliberately left for a follow-up, once there is measured data to build it on.
