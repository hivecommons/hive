- Failed hosted-spoke provisioning no longer leaks its Kubernetes namespace and PVCs ([#5768](https://github.com/hivecommons/hive/issues/5768)). `kubectl apply -f` is not transactional and the Namespace is the **first** object in the provisioning manifest, so a failure on any later object — a PVC the cluster cannot bind, a rejected Deployment — left the namespace and everything applied before the failure on the cluster while `provisionHive` returned an error and both of its callers did nothing but set `Status="error"`. Nothing else ever revisited it: `deprovisionHive` is a complete teardown but is reachable only from the user-initiated delete handler, and a hive that never finished provisioning is never offered for deletion, so the one function that could have removed the namespace was never called for precisely the hives that leaked it. The residue accumulated into dozens of orphaned `hive-hosted-hosted-*` namespaces holding ~76 stuck pods (64 Unschedulable, 12 Pending on unbound PVCs) on a shared CI cluster, where it became permanent noise in every health surface that counts pod issues and forced a console-side badge-attribution workaround. Provisioning now tears down the partial namespace on the failure path, deliberately using a **narrow** delete rather than the full `deprovisionHive`: the hive record must survive so the failure can be reported and retried, and the OCI export/file system that teardown would also remove may predate or be shared with the attempt.
- Hosted namespaces are now stamped at creation with `hive.kubestellar.io/owner=provisioner`, `hive.kubestellar.io/ephemeral=true` and a `hive.kubestellar.io/created-at` timestamp, so an orphan is identifiable from what it *is* rather than guessed at from its name prefix. The labels are written by the provisioning manifest itself, in the same apply that creates the namespace — a follow-up `kubectl label` call would be missing on exactly the failed-provision namespaces this exists to find.
- **Unit tests can no longer provision against a real Kubernetes cluster** ([#5768](https://github.com/hivecommons/hive/issues/5768)) — the mechanism that put the leaked namespaces on a live CI cluster in the first place. `ClusterConfig.InCluster` is a *claim*, not a fact: `loadClustersChecked` synthesises a default registry entry with `InCluster: true` whenever `clusters.json` is absent, which is the case in every test (the helpers point `clustersConfigPath` at an empty `t.TempDir()`). `kubectlArgsForCluster` then added `--server`/`--token` only when `KUBERNETES_SERVICE_HOST`/`_PORT` were set — and outside a pod they are not — so it added **no connection flag at all** and `kubectl` fell back to its ambient `~/.kube/config` or `$KUBECONFIG`. Any test reaching a provisioning entry point therefore issued a **real** `kubectl apply`, creating a real Namespace, Deployment and PVC on whatever cluster the runner was pointed at, named after the test's own fixture org. This is why the leaked namespaces are this package's unit-test fixtures character for character (`hive-hosted-hosted-acme-repo-abcd`, `…-apporg-repo1-*`, `…-myorg-repo1-*`) — six of the seven test files that drive `handleCreateHive` never install the scripted fake `kubectl`, and the fake was only ever a `PATH` prepend, which constrains *which binary* runs but not *which cluster it talks to*. An `InCluster` claim with no ServiceAccount environment now aims at the existing unreachable-kubeconfig sentinel, so the command fails loudly and locally instead of succeeding quietly somewhere real. Genuine in-pod behaviour is unchanged.
- A new bounded janitor sweep reaps leaked hosted namespaces as a backstop for when the inline teardown itself fails or the hub dies before reaching it. It runs inside the hub's existing SHA-poller reconciliation lane — no new goroutine or scheduler — throttled to a 15-minute interval, capped at 20 deletions per cycle, and logging every namespace it reaps with its age. Its selection is guarded four ways, and the first is an invariant tested as a property rather than by example: it **never** touches a namespace lacking `hive.kubestellar.io/ephemeral=true`, so an operator's hand-made or restored namespace that merely shares the `hive-hosted-` prefix is out of scope by construction. It also spares any namespace whose hive is still in the hub registry (every hosted namespace carries the ephemeral label, so the registry cross-check — not the label — is what separates a leak from a running spoke), anything younger than a 6-hour threshold (~72x the 5-minute provisioning timeout, so an in-flight provision cannot be reaped out from under itself), and anything already Terminating. An empty registry makes the sweep refuse to run rather than treat the entire fleet as leaked. Set `HIVE_HUB_NS_JANITOR_DRY_RUN=true` to have it report what it would delete and delete nothing, so the selection can be validated against a real cluster before it is trusted to act.
