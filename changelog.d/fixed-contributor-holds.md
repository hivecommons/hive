- A contributor who cannot push to their fork of a repository is no longer handed more tasks from that repository. A fork far behind upstream, with a token that lacks the `workflow` scope, makes GitHub reject every push, so each task there cost about ten minutes of agent time and ended with no pull request; the hub kept assigning them (six of one contributor's eleven tasks in two days on a production hive). When a task now ends this way, failed or complete without a pull request, the hub holds that repository back from that contributor for 6 hours, then 24, then 72 on repeats. The hold is immediate when the report shows the rejected push together with the missing `workflow` scope; a report that only says the push to the fork was refused books it the second time within 24 hours, so one ambiguous sentence does not cost anyone a repository. The hold covers every relay session of that contributor, since the fork belongs to the account. Other contributors still get those issues, and the held contributor still gets work from other repositories. A pull request from them in that repository that the hub verifies clears the hold. The relay prints what happened and how to fix it (use **Sync fork** on the fork's GitHub page, or run `gh auth refresh -h github.com -s workflow`), with no relay update needed. Operators see active holds on the dashboard's Contributors card and in `repo_push_holds` on `GET /api/contributors` (the admin MCP's `contributors_list`). Holds survive a hub restart; there is no new setting. This is the contributor-side half of [#11775](https://github.com/hivecommons/hive/issues/11775) and [#11776](https://github.com/hivecommons/hive/issues/11776), which stopped such a report from parking the issue for everyone.
- A contributor whose AI provider account is out of quota is no longer handed issues until the quota is back, and the issues they could not work are no longer penalised for it. A relay on a plan that had hit its weekly limit kept asking for work: each task failed in about two seconds with `You've hit your weekly limit · resets Dec 1, 3pm (UTC)`, booked the ten-minute failure cooldown on the issue, counted toward the issue's six-hour quarantine, and ten minutes later the same contributor took the same issue again (twelve such failures in thirty hours on a production hive). The hub now recognises that failure and holds that relay session out of all repositories until the reset time the provider stated (or, when it states none the hub can read, for 30 minutes, then 1, 2 and 6 hours as it repeats; never less than 15 minutes). The issue is treated as let go, not failed: it waits the usual 10 minutes and is then offered to another contributor, and such failures never add up to the six-hour quarantine. A task that completes with something to show for it lifts the hold, and the contributor's relay on another backend is not held. An authorization refusal (403, "not allowed to access model") is never treated as quota. The relay prints why it is not being offered work and until when, with no relay update needed. Operators see active holds on the dashboard's Contributors card ("Out of provider quota until ...") and in `quota_holds` on `GET /api/contributors`. Standby dispatch skips a held relay too. Holds survive a hub restart; there is no new setting. This is the hub-side cooldown exemption [#6541](https://github.com/hivecommons/hive/issues/6541) asked for; fix-pr tasks are not covered.
