- The contributor relay's PR review cycle now reviews the contributor's actual open PRs, and only runs when there are new ones to review ([#6664](https://github.com/hivecommons/hive/issues/6664)). It scoped the review to the repo of the single task that had just finished, and it fired on completions rather than on PRs shipped — so a contributor working across eleven repos had PRs in ten of them permanently unreachable (the cadence is per-five-completions, not per-repo, so coverage never catches up), and a task that correctly concluded `no_work_needed` still advanced the counter while guaranteeing that repo had no new PR. Observed: a cycle whose five triggering completions were *all* `no_work_needed` ran `gh pr list --repo projectbluefin/utah --author @me --state open` against a repo with zero PRs, while twenty open PRs across eleven repos went unreviewed. The cycle is now account-scoped (`gh search prs --author @me --state open`, which spans every repository including PRs from earlier sessions), names the repos work landed in as an ordering hint rather than a filter, and runs only when at least one PR has shipped since the last review — which also skips it entirely when there is nothing to follow up on, without a second API call. A skipped cycle defers rather than starves, and a review cycle's own completion never counts as shipping, so a cycle cannot re-arm the next one off the PRs it was merely reading. The prompt now also asks for `HIVE_VERDICT: complete`: the review cycle was the one task type that never got #5376's completion sentinel, purely because its prompt is assembled in the relay rather than by the hub, so it could previously only finish through the terminal-chrome inference #5353 documents as having produced thirteen separate issues.
