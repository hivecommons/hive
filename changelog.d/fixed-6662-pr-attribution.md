- The contributor relay no longer credits a contributor with a PR they did not open, or discards a correct `no_work_needed` verdict because one was visible on screen ([#6662](https://github.com/hivecommons/hive/issues/6662)). `detectPRURL()` is a regex over the agent's pane and cannot tell a PR the agent **opened** from one it merely **read about** — and `gh pr list` / `gh issue view --comments` both render full URLs, so an agent researching prior art prints plenty of the latter. When it matched one, the relay reported it as this task's `pr_url` *and* the `prURL ? null : verdict` precedence threw away the agent's explicit verdict. That precedence read "a visible PR contradicts 'nothing shippable'", which is true of a PR this task opened and exactly inverted for a PR a maintainer merged a month ago — where the PR is the evidence that makes the verdict correct. It therefore defeated [#3987](https://github.com/hivecommons/hive/issues/3987) in precisely #3987's target population, where a merged reference PR is present by construction and the agent must cite it to justify the verdict at all; the issue was then booked as shipped and re-entered the offer pool when no merge materialised. Measured over one 45-minute session, 3 of 10 completions misattributed a third party's already-merged PR and lost a correct verdict, with the split falling cleanly on whether the agent happened to print a bare `#1103` or a full URL. A scraped URL is now a candidate rather than a conclusion: it is checked against GitHub for authorship and recency, a PR that merged or was created before the task started is dropped and the verdict stands, a confirmed PR suppresses the verdict exactly as before, and a PR that cannot be verified (no `gh`, offline, rate-limited) is still reported as an audit trail but no longer silently outranks the agent's own sentinel. The cross-repo fallback — the first PR URL in any repository when none matched the task's — is removed: for a value the hub books cooldowns on, an approximate audit trail is a wrong one.
