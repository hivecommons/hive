- A contributor relay whose provider has refused it on quota now stops asking the hub for work until the quota resets, instead of failing one task per assignment for the whole window ([#6541](https://github.com/hivecommons/hive/issues/6541)). Detection landed earlier; the remaining defect was what happened next. Every cycle was correctly classified as a fatal provider refusal, and the relay then advertised `ready` and took another task, which hit the same wall seconds later — two rejections 45 seconds apart carrying distinct provider error IDs, so each one genuinely spent a provider round-trip, a hub assignment slot, and a hive issue marked failed, for a window agy itself stated as `Resets in 4h42m28s`. Quota is a property of the provider *account*, not of the task: it applies to every task the contributor could be given, and it expires. The relay now parks the loop — `ready` is withheld at the single point every frame passes through, a pushed assignment is declined immediately so another contributor can take it, and the hold runs to the reset time parsed off the provider's own banner (with a bounded fallback when none is stated, and a cap so a malformed countdown cannot wedge a contributor out of the fleet). The operator gets one clear message naming the provider, the wait, and the remedy, where previously the banner was visible only inside the agent's pane while the log said `[environment]`; and the task failure now reports a provider quota refusal rather than reading like a broken contributor host. Authorization refusals are unchanged: a 403 is not time-bounded, so it still fails fast and the relay stays available.
