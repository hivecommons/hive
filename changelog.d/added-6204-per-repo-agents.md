- An agent can now be scoped to the repositories it serves, so which agents exist is a per-repo answer instead of a hive-wide one ([#6204](https://github.com/hivecommons/hive/issues/6204)). Hive could already vary what an agent KNOWS per repo — `AGENTS.md` injection, repo-local skills — but not which agents there are, so in a hive holding a Go service next to a Rust CLI next to a Terraform module a specialist added for one of them woke on cadence and hunted for its concern in all the others: inference spend and issue noise on repos that never wanted it. Set `repos:` on an agent (in `hive.yaml`, in the dashboard's agent config dialog, or via `PUT /api/config/agent/{name}/general`) and it is handed work only on those repos, its kick lists only those repos, and its `$HIVE_REPO`/`$HIVE_REPOS` follow. Omit it — the default, and every agent in every existing config — and nothing changes. Enforcement is deterministic rather than a prompt instruction: the MITM proxy answers an out-of-scope agent write with a 403 whatever ACMM mode it holds, and the `hive-open-pr`, `hive-merge` and `hive-open-issue` relays refuse to fulfil one (they must: the proxy hard-denies direct PR creation and merge for every mode, and the hive's own fulfilment never traverses the proxy). Reads stay open on purpose, as does the hive's control plane. The bring-your-own-agent contract gained the same `repos:` key as an OPTIONAL interface rather than a sixth `AgentSpec` method, so no existing third-party spec stops compiling. The field carries the `repos_owner` marker the model/backend/pause fields already have, so a future ACMM pack cannot silently widen a specialist back to the whole hive.
