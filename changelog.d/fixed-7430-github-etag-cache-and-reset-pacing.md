- The hive stops burning its GitHub App quota on unchanged data and stops re-exhausting it the instant a window resets ([#7430](https://github.com/hivecommons/hive/issues/7430)). The projectbluefin spoke's 6,650/hr installation allowance was gone within one second of every reset (`rate limit was reset 1s ago` on a 403), so all 16 repos failed to enumerate and the scheduler ran blind: 21 issue/PR list sites re-listed the same repos every cycle with no `If-None-Match`, go-github's queued callers all fired at the reset boundary, and a cosmetic "commits behind stable tip" compare retried ~1/s against the exhausted limit. Now: (1) the shared GitHub transport makes every repeat `GET` conditional — it remembers each JSON response's `ETag` and body (keyed by requesting identity, URL and `Accept`, bounded in size and evicted LRU), sends `If-None-Match`, and replays the remembered `200` on `304`, which GitHub does not charge; go-github and every sweep above it see an ordinary response (`X-Hive-Cache: revalidated`); (2) a primary-limit `403` (`X-RateLimit-Remaining: 0`) now engages the same ten-minute post-reset slow start the secondary limit already had, from `X-RateLimit-Reset` (capped an hour ahead), so the post-reset wave is a ~2 s-spaced trickle instead of a stampede; (3) the App installation client goes through that chain at all — it used to hit the raw shared transport, outside both behaviours; (4) a failed stable-tip compare is remembered for five minutes instead of being retried on every status build. Enumerate-once-per-cycle fan-out, GraphQL enumeration and `since`-based incremental listing remain follow-ups; a failed all-repos enumeration already keeps the previous cycle's work list rather than feeding agents an empty one.
