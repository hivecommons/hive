- **A "Let hive decide" direction no longer blocks a PR after you approve it.** When the delegate answered a parked contributor or adopted PR with a direction, the hive stored it under your name, and the stage then read it as your own change request on that commit: the PR showed `human-changes-requested`, and the dashboard's Approve stayed disabled ("needs a new commit") even after you approved the same commit on GitHub. A direction that only needed a PR-body edit never got that commit, so the PR stayed stuck. The hive's own direction is not a maintainer's change request ([#15063](https://github.com/hivecommons/hive/pull/15063)), so a direction the delegate records is now marked as the delegate's, and a trusted maintainer's approval of the same commit after it supersedes it: the commit reads as approved, the fixer is not sent for the direction again, and Approve works. This holds for that commit only, and not when a person's changes-requested review stands on it or was carried onto it over the hive's own merge of the base branch. If the approval is dismissed, the direction stands again; once the hive merges the base branch in, neither moves to the new commit. On the hive's own PRs nothing changes here: as before, any trusted approval submitted after a recorded decision, typed or delegated, supersedes it unless a changes-requested review stands on that commit. A direction you type yourself on a contributor or adopted PR (`/hive decision <text>` or Give direction) is handled as before, and so are delegated directions recorded before this release, which carry no marker. One more change on every lane: a GitHub read that fails (a rate-limit window or an outage) no longer revokes an approval the hive recorded from a review; only a read showing the review dismissed or replaced does.
