- CI runner labels are now a repository variable with a GitHub-hosted default, so a fork of this repository can run its own CI ([#6083](https://github.com/hivecommons/hive/issues/6083)). 24 `runs-on:` declarations across 12 workflows named the `[self-hosted, hive]` fleet directly, which only `hivecommons` has. In a fork those jobs did not fail — they queued forever, held their workflow's concurrency group so the next push queued behind them, and could not be cancelled, because there is no runner to deliver a cancellation to. Measured on a fork of `v4`: one pull request produced 26 runs, 14 still `queued` an hour later, and a cancel request returned `202 Accepted` while the run stayed `queued` 22 minutes on. Every such `runs-on:` now reads `fromJSON(vars.HIVE_RUNNER_LABELS || '["ubuntu-latest"]')`, so a fork that sets nothing runs on GitHub-hosted runners and a fork with its own fleet can point at it. Each job keeps whatever fork-PR guard it already had — only the label source changed. **`hivecommons` must set `HIVE_RUNNER_LABELS` to `["self-hosted","hive"]` at the org or repo level**, or the heavy lanes move to `ubuntu-latest` on merge; `src/docs/ci-runner-labels.md` carries the command, how to clear runs already wedged, and why the fallback sits inside `fromJSON`'s argument rather than relying on `&&` short-circuiting. `src/deploy/test_runner_labels_portable.sh` fails CI if a `runs-on:` names the fleet directly or drops that fallback.
