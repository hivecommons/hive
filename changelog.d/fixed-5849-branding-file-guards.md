- The dashboard now refuses branding files it cannot vouch for, closing a CSS-injection path into the operator's own dashboard ([#5849](https://github.com/hivecommons/hive/issues/5849)). `handleBrandingCSS` previously did a bare `os.ReadFile` and served the bytes as `text/css` with no ownership, mode, or size check — and the default `<data>/branding/custom.css` resolves to the parent of `agents_dir`, the same volume agents write to. With `img-src 'self' data: https:` in the dashboard CSP, any agent that dropped a `custom.css` got its stylesheet rendered in the operator's browser and could beacon out through an image URL. Both `custom.css` and `branding.json` are now refused when the file is group- or world-writable, owned by neither the hive process user nor `root`, larger than 128 KiB (the same cap the `?style=` custom-stylesheets feature already applies — refused outright rather than truncated), or reached through a symlink that escapes the branding directory. A refusal 404s exactly like an absent file and logs once with the path, the offending mode or owner, and the `chmod`/`chown` that fixes it, rather than telling the browser why. Root-owned files and symlinks *within* the branding directory are deliberately accepted so the documented read-only Secret mount (`uid 0`, `defaultMode 0444`) and Kubernetes projected volumes keep working; `HIVE_BRANDING_ALLOW_UNSAFE_OWNER=true` waives the ownership check alone for deployments with a legitimately foreign owner.
