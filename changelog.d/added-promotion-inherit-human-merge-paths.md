- A branch-promotion rule can now let its promotions carry files a person must merge: `auto_merge.promotions[].inherit_human_merge_paths` (off by default). Until now a promotion that changed a file on the repository's `human_merge_paths` list was always left for a person, so where the listed files are the ones that change most (release and build workflows, for example) most promotions still needed a hand merge. With the option on, a promotion the lane owns (its head and its test merge carry exactly the source branch's tree, checked live when it is routed and again right before the merge) merges even when it changes a listed file. Know what that proves before you turn it on: the hive proves only that the promotion's tree is the source branch's current tree. It does not check how or when a listed file's content reached the source, so the option is not a record that a person merged it there. A listed file can reach the target although no person merged that content under the list when the path was listed after the content was already on the source; when a merge the list does not bind landed it there (the list binds only the hive's own merges, not another bot's or GitHub's own auto-merge, nor a person with merge rights); when a `human_merge_pin_only` exception or a bypass actor did; when the source is protected less than the target; when a single-commit promotion replaces a change a person made only on the target; or when the source is itself the target of a rule with the option on. Workflows triggered by a push to the target run as soon as the hive merges, and there is no carve-out for the workflow that opens promotions. Only the hive's own human-merge-path stop is lifted, and only on the promotion lane: a `hold` or `needs-owner-merge` label a person adds, the breaking-change title rule, `blocked`, exempt and sentinel labels, the review verdict hold, the intent gate, required checks, `squash_only` and both tree checks still apply, and a promotion that stops matching the source is left for a person as before. A `needs-owner-merge` label the hive itself put on such a promotion is removed once per head, with a comment, after the promotion is checked against GitHub again in that pass; a label a person set is never removed. That removal has two preconditions: it runs in the stage pass, so stage labels must be enabled (they are by default), and it goes through the write-back gate as `human_merge_path_release`, which for a pull request a workflow bot opened allows it only when the repository's write-back mode is `full` or the pull request carries the write-back opt-in label. Otherwise the label stays, the hive logs why once for that head and tries the same head again 30 minutes later, and a person merges the promotion or removes the label by hand, after which the lane merges it. To keep a promotion for yourself, add `hold`. Each merge that carried a listed file is recorded in the audit log (`promotion_decision`, `human_merge_paths=promotion-rule-option`, the first ten files and the tree SHA), and turning the option on or off is recorded on the `config_auto_merge` entry (`promotion_inherit_on` / `promotion_inherit_off`, naming the repository and target). Set it per rule in Settings → Features → Auto-merge → **Branch promotions that merge without a person** (the **Also merge files a person must merge** tick box) or with the admin MCP `auto_merge.update` `promotions`; turning it on is disclosed as widening, and `write_confirm` reads the rule back and warns (`inherit_human_merge_paths_stored: false`) if a hive on an older build stored it without the option. See [hive-merge.md](src/docs/hive-merge.md#branch-promotion-pull-requests).
