- The GitHub App credential surface now describes the **write path**, and names an org transfer as an org transfer ([#5774](https://github.com/kubestellar/hive/issues/5774)). When the repository moved from `kubestellar` to `hivecommons`, every agent branch push started failing while issue creation kept working — and nothing said so: `DiagnoseAppAuth` classified solely on the Issues permission, so a hive that could file issues and could not push a single branch reported exactly what a healthy one reported. The diagnosis now also records the grants a pull-request flow actually runs on — Contents (push the branch), Pull requests (open the PR), and Workflows (needed when the diff touches `.github/workflows/**`) — exposes them as `GrantsAgentPushFlow()`/`PushFlowGrants()`, and logs them on **every** credential verdict including the healthy one, since the installation that looks fine is the one worth counting. They are recorded, never enforced: requiring them would flip the read-only advisory tier, which holds Contents: read by design and never pushes, into a fault state for working as intended. Separately, a coverage miss whose shape is a transfer gets a new `repo-moved` state instead of `repo-not-covered`. That mattered because the two need opposite instructions — "tick the repository in the org's App installation" cannot be followed once the repository has left that account, and sending an operator to a settings page for an org the repo no longer belongs to costs them exactly the debugging time the deterministic coverage check was built to give back. The new verdict names where each repository lives now, states plainly that the App, key and installation are all healthy, and fires only when the shape is unambiguous: complete listing, the configured owner entirely absent from coverage, and exactly one covered repository carrying the configured name. Anything less falls back to the previous verdict rather than guessing.
