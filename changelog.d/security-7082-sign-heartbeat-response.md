- Hub→spoke heartbeat responses are now independently signed, closing the gap where config and (for hosted spokes) GitHub App credentials pushed in the heartbeat response were authenticated by the TLS channel alone ([#7082](https://github.com/hivecommons/hive/issues/7082), raised in the CNCF TAG-Security second review, cncf/toc#2286). The hub signs each response with the **same** Ed25519 key it already derives from the master seed for SSO/session tokens — no new key, distribution, or primitive — and binds the signed body to the `hive_id` (defeating cross-hive replay: a response captured for one hive is rejected by another) and a per-hive monotonic `seq`/timestamp (defeating rollback replay of an old captured response). Spokes verify with the public key they already hold (`HIVE_SSO_PUBLIC_KEY`). Rollout is **staged and safe by default**: a spoke verifies and logs but still **accepts** every response (`HIVE_HEARTBEAT_VERIFY=log`, the default), and only **rejects** unsigned/mis-bound/stale responses when an operator sets `HIVE_HEARTBEAT_VERIFY=enforce` **and** the spoke has already accepted one valid signed response (trust-on-first-signed) — so upgrading a spoke, or enabling enforcement, can never brick it against a hub that has not yet shipped signing. Operators must upgrade **hubs before enforcing on spokes**.
