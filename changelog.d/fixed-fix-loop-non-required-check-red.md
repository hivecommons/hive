- **The fix loop no longer treats a failing non-required check as red.** `HasFailingRequiredCheck()` was true for any failing non-meta check run, so a PR whose only red check was advisory (a `continue-on-error` job the branch ruleset does not require, which GitHub reports as unstable but mergeable) drew FIX-BEFORE-NEW re-dispatches with nothing to fix, spent the whole budget, and was parked with `needs-human` and `reviewer-handoff` (Danathar/tududi#467: 6 kicks on one head). It now consults the required set `EnrichCIStatus` already resolves for the blocked-PR pill: when that set is known and non-empty, every required check reported as a check run, and none of them failed, the PR is not red. The stuck-red reaper, the escalation ledger, the claim-suppression release and the dependency-bot red-CI handoff all follow it; the ledger treats such a PR as pending, so it keeps its history and an existing `needs-human` label stays put. An unknown or empty required set, or a required check that has not reported as a check run, still fails closed. The open-PR recommendation report keeps listing any red PR under "Failing CI" through the new `HasFailingCheck()`.
