- Codex in contributor **container** mode no longer asks for a bubblewrap sandbox the container cannot provide ([#6653](https://github.com/kubestellar/hive/issues/6653)). `--sandbox workspace-write` is implemented with bubblewrap, and bubblewrap's first act is to create an unprivileged user namespace — which the contributor container denies under the runtime's default seccomp profile. The result was not a weaker sandbox but no working command at all: every model-generated command died with `bwrap: No permissions to create a new namespace`, including *both* of Codex's patch-application paths, so the agent had to rediscover a working file-edit mechanism by trial and error on each task (one observed session burned five minutes and seven points of context on failed edits before landing anything). The error text also names a *host* sysctl, sending operators to reconfigure a machine that was never the problem. Hive now resolves the `--sandbox` value at launch instead of hard-coding it: it falls back to `danger-full-access` only when a root-owned marker proves an outer container boundary exists **and** an `unshare` probe proves user namespaces are blocked, and it prints one line saying which posture is in effect. **Local mode is never downgraded** — with no outer boundary there, a blocked probe leaves `workspace-write` in place rather than widening access to the operator's host (#4918). Relaxing the runtime with `--security-opt seccomp=unconfined` restores `workspace-write` automatically with no variable to set, and the contributor image now ships a real `bubblewrap` so that path uses a distro-maintained binary rather than Codex's bundled fallback. `HIVE_CODEX_SANDBOX_MODE` pins a value and skips the probe.
