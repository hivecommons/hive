- In a repository that requires every review conversation to be resolved, the hive now also resolves its own non-blocking review note when the only replies in it are from the pull request's author and the code has moved on since. Authors, and the agents working for them, often answer a note with "Addressed in `<sha>`" after pushing the fix. Until now any reply from someone other than the hive left the thread for a person ([#19421](https://github.com/hivecommons/hive/pull/19421), [#19826](https://github.com/hivecommons/hive/pull/19826)), so GitHub refused the merge and the PR parked at `085-needs-decision` with `unresolved-review-threads` until someone resolved the thread by hand. The hive now resolves such a thread when the commented lines changed after the note (GitHub shows the thread as outdated), or when the pull request has a newer head than the one the note was left on and the hive's own review approved that head after the author's last reply. The hive does not read what the reply says: "I disagree" is treated like "Addressed" once either of those holds, so an author who wants to stop the merge uses a hold label or a draft, not a reply. Everything else is as before: a reply from any other person or bot keeps the thread open, and so does the author's reply when neither of those holds; a blocking finding and a thread someone else opened are never resolved. It applies everywhere the hive already resolves its own notes: a refused merge or merge-queue enqueue, the serialized lane, and a head handed to a person at `090-ready-for-human-merge`. There is no new setting, and `review.severity.block_at: P3` still turns the whole behaviour off. Threads resolved this way are counted as `own_author_answered` in the lane's log lines, and their audit entries carry `rule=pr-author-replied`.
