- The contributor relay no longer loses a `task_complete` to the hub's 64 KiB WebSocket read limit, which put headless contributors in a reconnect loop that re-ran tasks they had already finished ([#7932](https://github.com/hivecommons/hive/issues/7932)). The captured-output tail was sent as fifteen *lines* with no byte bound, and a JSON-streaming backend such as pi puts a whole tool event — embedded diff and all — on one line, so a successful task reported its completion in a frame the hub refused with `1009 message too big`; the hub's lease outlived the close, the same task came back, and the agent redid work it had already shipped (four times over on a live spoke, one run having opened a real PR). Frames are now clamped where every frame passes through: the audit tail is held to 8 KiB and the whole frame to the hub's limit, shrinking only payload fields — `task_id`, `result`, `pr_url` and `verdict` always survive intact, and a trimmed tail carries a visible marker. The hub now states that limit on `auth_ok` as `max_message_bytes`, so a hub that raises its ceiling carries its relays up with it instead of the two numbers drifting apart, and it logs a frame that trips the limit rather than disconnecting a contributor with nothing in the hub log.
