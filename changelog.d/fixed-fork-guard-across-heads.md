- A fork PR waiting on a check only a maintainer can run (a fork-guarded check such as a fork Canary) stays with the maintainer across new heads. On projectbluefin/utah-packages#869 and #862 each new head (a merge of the base, or the author's push) read as an ordinary red check until the next enumeration read its annotation, so the PR dropped to 072 and the author was nudged to fix a check they cannot fix. #862 got 13 hive merge-of-main commits, each discarding the exact-head run it waited for. The recorded `fork-guard:` reason now carries onto a new head while the same check is red, the hive no longer updates the branch of a fork head waiting on a fork-guarded check, and the 085 ask names the head the maintainer must run the check for.
