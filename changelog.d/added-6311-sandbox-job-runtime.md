- Sandboxed agent kicks can now run as a Kubernetes `Job` instead of a rootless Podman container on the hive pod's own node ([#6311](https://github.com/hivecommons/hive/issues/6311)). Set `sandbox.runtime: job` on an agent (or `agent_sandbox.runtime: job` globally) and describe the workload under `job:`: the image, a `node_selector`, `resources` limits such as a device count, `tolerations`, `env_from_secrets`, extra PVC `volumes`, and a `ttl_seconds` for the finished Job. This is how an agent's kicks reach a different runtime than the hive image and a node with accelerator hardware, the roadmap's "Kubernetes-native agent sandboxes" direction. The executor is unchanged: hive clones and branches the workspace on its own data PVC as it does for Podman, the Job mounts that same claim (`job.workspace_claim`, which must be ReadWriteMany when the Job lands on another node), and after the Job exits hive reads the commits back and the existing push broker and PR path take over. The credential boundary is stated rather than implied: the Job receives only the Secrets named in `env_from_secrets`; hive's brokered GitHub token never enters it, so a Job cannot push or open a PR itself. Logs, exit code, timeout, and the PR link land on the agent card like any sandboxed kick, and the finished Job is left in place until its TTL on failure so an operator can inspect it. The spoke ServiceAccount needs a Role for `batch/jobs` and `pods`/`pods/log`; the standalone kustomize base and the hub provisioner now grant it. `pkg/kubejob` is the launcher, `config.AgentSandboxGateWarnings` names a job-runtime agent with no claim or an unknown runtime at boot and on reload.
