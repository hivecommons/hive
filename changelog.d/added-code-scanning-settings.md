- The code scanning sweep can be turned on and tuned from the dashboard and the admin MCP, not only by editing `hive.yaml`. Until now `code_scanning` was YAML-only, so a hosted hive, or an owner without access to the server file, could not use the sweep at all. Settings → Features has a new **Code scanning issues** section: a switch for every repository, a per-repository switch (hive-wide, on or off) for each `project.repos` entry, the minimum severity, the per-pass cap, the interval, the tool list and the extra rules to leave out. Next to each repository's switch it shows what the last sweep pass recorded there: the App can read the alerts, the App cannot (the `security_events` permission is missing), no code scanning analysis, the last pass failed, or not checked yet. The same settings are served by owner-only `GET` and `PUT /api/config/code-scanning`, by the admin MCP `settings_read` section `code_scanning`, and by the new `code_scanning.settings` write operation, which goes through `write_preview` and `write_confirm` like every other write. A change is checked exactly as `hive.yaml` is on load, with the same messages, and nothing is saved when it fails. A saved change is written to `hive.yaml`, audited as `config_code_scanning` with one entry per changed key and its value before and after, and used by the sweep from its next pass without a restart. `repos` is sent whole: changing one repository keeps every other repository's override, and a repository set back to "hive-wide" keeps its own severity, tool, rule and cap overrides. Those four per-repository overrides are shown in the dashboard and edited through the API, the admin MCP or `hive.yaml`. Nothing changes in what the sweep files, and granting the GitHub App the `Code scanning alerts: Read-only` permission is still the operator's step. See `src/docs/code-scanning.md`.
