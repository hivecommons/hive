- The server now places every open issue and pull request in one Overview *card band* that says who has the next move (Your turn, Yours to close, Covered by an open PR, Waiting on another item, Human placed on hold, Reporter to confirm the fix, Author to update the PR, Dependency bot to rebase, Queued for agents, Agents are working it, Will merge on its own, Not work, Draft, Held, or Unexplained), grouped into six tiles that add up to the open totals. It is display data only: it reads what the hive already decided (the your-turn decision, the row facts, the contributor queue's verdicts and the recorded stages) and changes no decision, inbox, export column or other existing field or MCP value. `/api/status` and SSE carry an `overview_card` block and `card_band`, `card_group` and `card_reason_code` on each row; the Overview CSV and JSON exports append `card_band`, `card_group`, `card_reason` and `card_reason_code` after today's columns, accept `card_band=` and `card_group=` filters and add `card_bands[]`, `card_groups[]` and `card_remainder`; the `issues_by_band` and `prs_by_band` MCP tools accept optional `card_band` and `card_group`; and the trend history samples the six tiles as `overviewCard*`. To read the contributor queue's reasons without running it again, the status refresh now keeps the refusals of the admission pass it already runs for standby dispatch; the queue it builds is unchanged. One existing value changes: `openItems.buckets.blocked` in `/api/status` (and so in the `fleet_status` MCP tool), and the "Blocked" count in the meeting and chat status line built from it, now read the PR equation's `blocked` term, which they had been reading under a name that does not exist (they always said 0). The dashboard card that draws these bands follows separately.
