- `just contribute-hive <backend> local` now passes `HIVE_WORKSPACE_DIR` to the agent CLI on the launch line, so the task prompt's `$HIVE_WORKSPACE_DIR/<owner>/<repo>` resolves ([#6707](https://github.com/hivecommons/hive/issues/6707)). The recipe exported the variable, but that export reached the agent's tmux pane only when `tmux new-session` had to *start* a server. Running the recipe from inside tmux — a normal way to run a long-lived contributor — made `new-session` join the already-running server instead, and the pane inherited that server's environment, which predates the export. The prompt's path then expanded to `/<owner>/<repo>` at filesystem root and `gh repo fork --clone` failed with `could not create leading directories … Read-only file system`, *after* the fork had already been created on GitHub, leaving the agent to recover by hand. `-c "$HIVE_WORKSPACE_DIR"` on the same line sets the pane's working directory and not its environment, which is why it did not cover this. The variable now travels as a `VAR=value` prefix beside the build-cache variables — the technique the comment there already recommends for exactly this reason — and relaunches pick it up too, since the relay reuses the same `AGENT_LAUNCH_CMD`. Container mode was never affected: `contributor-agent.sh` exports the variable and starts that container's own tmux server in the same process.
