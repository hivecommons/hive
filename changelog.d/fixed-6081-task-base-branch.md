- Contributor task prompts no longer tell an agent to base its work on the branch the *hive binary* was built from when the issue is in someone else's repository ([#6081](https://github.com/hivecommons/hive/issues/6081)). `taskBaseBranch` passed `upstreamBranch()` through for every task, so a self-hosted hive built from `v4` stamped `v4` onto 100% of its tasks — observed on a hive dispatching for four repositories whose default branch is `main`, none of which has a `v4` at all. That case was loud only because a missing branch fails visibly; a repository that happens to have a `v4` which is not its default would have resolved, opened the PR against it, and satisfied the prompt's own "confirm the base" step — wrong base, no error anywhere. The hive's build branch is now inherited only when the task's repository is the hive's own; every other task gets the existing instruction to resolve that repository's `defaultBranchRef`, which until now was unreachable code. A release-line title (`[v5] ...`) still overrides both, since that is a statement about the work rather than the repository. Because that fallback wording is now the common path rather than dead code, it also gained the operational detail the named-branch wording already had — `git fetch upstream`, an explicit `git checkout -b` from the resolved branch, and a confirm-the-base step — so the half of [#5729](https://github.com/hivecommons/hive/issues/5729) that matters (never trust the branch the reused checkout is sitting on) holds either way.
