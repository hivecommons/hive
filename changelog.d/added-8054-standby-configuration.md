- Hive now accepts and validates the standby-contributor configuration surface from [RFC #7629](https://github.com/hivecommons/hive/issues/7629) — a per-lane `standby:` block (`enabled`, `min_model_capability`, `daily_cap_per_contributor`) plus the hive-wide `hub.standby_contributors` approved list, `hub.standby_model_tiers` mapping and `hub.standby_allow_private_repos` opt-in ([#8054](https://github.com/hivecommons/hive/issues/8054)). Nothing reads the block yet: it is the configuration half of a feature whose pause signal, relay mode, matching and dispatch land in later phases, so a hive that writes no `standby:` block is unaffected. What it does do is fail the load on the misconfigurations that would otherwise be silent — a lane switched on with nobody approved, a floor spelled `unknown` (the absence of a capability tier, not a weak one, and a floor anything would clear), a negative daily cap, an approval entry that is not a GitHub login, or two tier-map rows disagreeing about one model configuration. An omitted floor defaults to `T1`, the strongest, and an omitted daily cap to `0`, which dispatches nothing — so adopting the block early is safe. The floor stays readable-only on every surface, with a test that scans every route and client file to keep it that way: lowering it is an edit to `hive.yaml`, never a control, and no surface suggests it. See [the standby design record](https://github.com/hivecommons/hive/blob/v6/src/docs/design/standby-contributors.md) and [agent configuration](https://github.com/hivecommons/hive/blob/v6/src/docs/agent-configuration.md).
