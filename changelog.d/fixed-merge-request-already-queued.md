- The merge-request watcher no longer treats a PR that is already in GitHub's merge queue as a failed merge. A `hive-merge` request for a queued PR got `405 Pull Request is in the merge queue.` from `PUT /pulls/{n}/merge`; the watcher retried it three times, set the request aside as `.exhausted` and logged `merge failed, giving up after max attempts` at WARN, for PRs that then merged through the queue minutes later, and an agent that re-filed the request repeated the cycle. That refusal now settles the request on the first answer: the `.result.json` reads `"ok": true, "queued": true` with a `note` (no `sha`, since nothing has merged yet), the request file and its per-PR wait state are removed as after a merge, one INFO line is logged, no attempt is counted and no operator alert or fix-loop re-engagement fires. The ruleset refusal `Changes must be made through the merge queue` keeps its existing handling. If the PR leaves the queue unmerged, a new request is processed normally. See `src/docs/hive-merge.md`.
