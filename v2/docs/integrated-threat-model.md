# Integrated Hive Threat Model

## Trust boundaries

- Pull-request code is untrusted. PR workflows receive read-only permissions, no lifecycle credential, and no protected-target secret. Generated workflows never use `pull_request_target` to execute PR code. Repository-owned workflow provenance authenticates the GitHub Actions App, path, event, and head, not the semantics of candidate workflow source. Hive refuses autonomous merge of workflow-changing PRs and verifies exact managed bytes on the default branch before each production run, but it cannot prevent a repository administrator or human from merging outside Hive. Production repositories must protect workflow and Hive-policy paths with independent code-owner review, stale-approval dismissal, strict required checks that include administrators, and no unreviewed bypass; otherwise use non-merging authority.
- The maintained fork enables repository-enforced GitHub release immutability before publication, so published assets and their associated tag cannot be replaced. Release installation begins with a data-only `gh release download`; the installer script is never piped from the network into a shell. Its attestation must match the fork repository, exact integrated release workflow, exact `refs/tags/<version>` source ref, the tag's immutable commit as both source and signer digest, and a GitHub-hosted runner before execution. The installer applies the same policy to the distribution archive and re-resolves the tag after verification to close tag-move races.
- Protected target workflows produce deterministic Visual Hive evidence. Evidence is not trusted because the producer says it is trusted; Hive independently verifies GitHub repository identity, run, artifact, conclusion, event, exact SHA, attestation requirement, expiry, and replay key. Repository-test lifecycle evidence has a separate authority boundary: every configured command runs in one isolated GitHub-hosted job, and Hive exhaustively verifies the exact selected run, workflow, head, expected job topology, named command step, and required Visual jobs through GitHub's Actions API. Target-written ledgers, step outputs, summaries, and artifact text are diagnostics and never authority for opening or resolving a repository-test finding. The hosted controller is triggered by both `schedule` and `workflow_dispatch`, with GitHub Actions concurrency serializing operations. Each production evidence dispatch still uses a required 256-bit correlation input and exact run title; Hive durably binds that correlation and the resulting run ID before consuming evidence, so a concurrent or newer manual run cannot cross either boundary.
- Hosted durability is repository-owned but not repository-trusted. Bootstrap creates one dedicated `hive/state-<repository-id>` branch and one create-only `HIVE_HOSTED_STATE_KEY` Actions secret. The branch contains exactly one bounded canonical state bundle; its HMAC-SHA256 key never appears in the branch, workflow, logs, or artifacts. A fresh runner accepts only regular, unlinked, private, allowlisted files whose signed metadata binds repository identity, branch, exact release, trusted controller workflow, sequence, and prior commit. It verifies the remote head and parent before restore, and every mutation checkpoint advances the branch with an exact-parent compare-and-swap. A parallel run, force-push, history rewrite, cross-repository state, unknown file, permission drift, or torn checkpoint fails closed.
- Trusted Visual Hive ingestion accepts neither `pull_request` nor `pull_request_target`. It requires bundle v3, an exact match between `producer.gitCommit` and Hive's configured 40-character Visual Hive release commit, the exact approved managed workflow name/path, a non-empty duplicate-free capability-parity receipt whose per-domain counters reconcile with canonical baseline/current-inventory identities, and a separately downloaded full source artifact that exactly matches the complete content-addressed index. Provenance verification alone sets neither Hive's trusted bit nor resolution authority; both are established only after that full source comparison succeeds, lifecycle application rejects untrusted validation state, and lifecycle closure consults this Hive-validated authority state rather than the producer's raw `scan.authoritativeForResolution` claim. Derived repository-test authority requires that same independently verified, complete-source parent. Local v3 ingestion remains trusted only for present/open/update compatibility and cannot resolve findings. Bundle v2 remains readable solely as advisory local repair evidence: `source.trusted`, `scan.authoritativeForResolution`, and absent findings cannot grant it resolution authority. A future executor/broker authority path must introduce an explicit versioned digest-bound receipt rather than infer authority from producer fields.
- Target dependencies, repository tests, browsers, and the target-facing Visual Hive collector run under a dedicated unprivileged account with an empty allowlisted environment. Before any target process starts, the workflow moves the immutable Visual Hive CLI outside the checkout, makes the tooling, Git metadata, configuration, and pull-request scope input root-owned and read-only, then kills the target account and verifies the exact checkout and CLI again. After that kill, the runner removes any target-precreated path and root-creates a read-only receipt for the actual Visual pipeline step outcome before uploading evidence. Raw target artifacts are treated as hostile input: a separate fresh GitHub-hosted job rebuilds the exact pinned CLI, rejects symlinks and oversized trees, deletes target-authored plan artifacts, regenerates the full plan from the immutable CLI and configuration, and binds every reported contract result one-to-one to that fresh plan before it can become a resolution scope. A failed runner outcome remains usable as present/failing evidence but grants no absence or resolution authority. The fresh job also regenerates the verdict, issues, baselines, and authoritative lifecycle bundle without running repository code. This isolates lifecycle authority from target scripts, but no test runner can prove that the target application is semantically honest while it is being exercised: application code can detect the test environment, alter its own runtime behavior, or evade an assertion. The boundary authenticates runner provenance, immutable inputs, process identity, and evidence transformation; it does not make adversarial application behavior benign. Protect workflow and policy paths independently and use non-merging authority when repository administrators are not trusted.
- A pre-existing repository-test failure cannot turn PR-authored text into setup authority. Local Hive re-reads the exact same-repository managed PR and creates a successful `hive/setup-authorized/<binding-sha256>` commit status as the authenticated numeric GitHub `User`. The read-only authorization job recomputes a binding over repository ID/name, PR, base/head refs and SHAs, authorizer ID, canonical raw diff and old/new blob bytes, required-file identities, and required-absent paths. It requires the latest exact context, creator ID/type, state, and PR target URL. Any mutation invalidates the authorization. This exception can install only the exact managed setup while the Visual verdict is green; it cannot authorize application/dependency changes or act as production finding evidence.
- A workflow-dispatch transport error without an HTTP response is an explicit ambiguous state, not permission to retry. Hive performs exhaustive exact-correlation discovery once and releases the production lease if no run exists. Operator recovery uses read-only plan followed by apply, bound to immutable repository identity, request digest, action, authenticated actor, plan digest, timestamp, expiry, and reason; apply repeats discovery and is audited before state changes. Revocation creates a new correlation on the next run. Same-correlation retry is break-glass because GitHub offers no atomic idempotency boundary: Hive searches again immediately before POST and rejects duplicate exact matches, but operators must prefer revocation unless they can establish that the original request was never accepted.
- Auto-merge protection is a second, post-merge activation phase. Hive first verifies the exact managed files and the production run's workflow path, name, `workflow_dispatch` event, default-branch ref, current head, durable correlation, and successful `visual-hive-production` Check Run. GitHub requires a recently successful context before it can become required, so that same exact production run contains one actively guarded `visual-hive` eligibility seed: it fails rather than skips unless event/ref/current-default SHA all match. Hive binds both jobs and Check Runs to the GitHub Actions App ID before it may create absent protection. Evidence application and every lifecycle writer remain behind that activation boundary. A crash retains the exact dispatch; an existing repository policy is inspected but never replaced.
- Hive is the sole GitHub lifecycle writer in integrated mode. Visual Hive standalone publishing must remain disabled while Hive integration is enabled.
- Repair agents run in isolated branches/worktrees. Central policy and the GitHub proxy authorize issue, branch, commit, PR, close/reopen, and merge operations independently of prompts.
- A generated repair or baseline branch name is not ownership proof. Every pushed tip carries exact `Hive-Repository-ID` and `Hive-Operation` trailers. Before advancing an existing remote ref, Hive fetches the exact observed tip, verifies those repository-scoped trailers, proves that tip is an ancestor of the new checkpoint, and pushes with a lease bound to the observed SHA. A collision, spoofed trailer on divergent history, or concurrent move fails closed without overwriting the branch.
- Setup treats its bootstrap state tree and checkout metadata as a no-follow boundary. Every existing state/checkouts/checkout/`.git` component must be an ordinary exact path; Unix links and Windows junction/reparse points are rejected before directory creation or Git. A markerless legacy checkout is never adopted from a Git-config substring because remote helpers, includes, hooks, credential helpers, and URL rewrites can execute before an origin check. Baseline proposal branch/commit identity is durable before push, and every security-relevant baseline phase carries an idempotent pending-audit receipt; a failed audit write remains blocking even after the external operation or `production_verified` data is durable.

## Supply chain

- Integrated archives have GitHub Sigstore build provenance and SHA-256 checksum assets.
- The installer pre-inventories archives and rejects path traversal, absolute paths, multiple roots, links/unsupported entry types, excessive entries/expanded bytes, duplicate or extra uninventoried files, symlinks/reparse points, digest/size drift, wrong platform, and missing required files before activation. The bundled Node validator must first match its exact manifest digest and runs without ambient `NODE_OPTIONS` or `NODE_PATH`. The installer also refuses to overwrite an unrelated same-named launcher or Codex skill; only an exact launcher owned by the recognized active distribution and an exact packaged skill inventory are replaceable. Activation failure restores the exact previous installation.
- `release-manifest.json` binds the Visual Hive payload to its exact commit and inventories every regular non-symlinked file. Hive verifies it before executing the CLI and in `hive doctor`.
- Generated Actions use immutable commit SHAs. Visual Hive workflow checkout uses an exact 40-character commit.
- Node is exact version 22.23.1; the Linux and Windows archive hashes are pinned in the read-only build job rather than trusted from a checksum downloaded beside the archive.
- Hosted state is release-bound. A controller restores only its exact current release identity or the one explicitly recorded predecessor during an upgrade/rollback transition, then checkpoints under the current identity. Skipping identities or running an older binary against newer state fails closed without rewriting the branch.

## Credentials

- Setup and explicit local mode use the GitHub CLI authorization flow; users never paste tokens into repository config. Hosted runs use only the job-scoped `github.token` with per-job minimum permissions.
- Hosted `repair-pr` and `auto-merge` setup provisions `OPENAI_API_KEY` through GitHub's encrypted Actions-secret API only when the fixed-name secret is absent. Hive may inspect secret metadata but cannot read, return, or rotate its value; a concurrent appearance fails closed. `advisory` and `issues` do not require it. The credential is exposed only to the trusted controller operation, never to target repository commands, evidence, logs, issues, or repair prompts. Explicit local mode retains the operator account's provider credential without writing it into repository configuration.
- Repair model execution accepts only an exact reviewed native Codex binary: release-gated `codex-cli 0.144.1`, plus the exact Windows desktop-packaged `codex-cli 0.144.0-alpha.4` build on Windows after matching the same reviewed inventory and probes. The binary is auto-detected from `PATH` or `CODEX_HOME/.sandbox-bin` or supplied by absolute `--provider-command`. Hive rejects `npx`, npm, shell, PowerShell, `.cmd`, shebang, script, positional package, path-wrapper, profile, sandbox, approval, and arbitrary config payloads; atomically consumes one Health attestation for one Run; and creates then strictly removes a separate sealed executable copy for each health check and invocation. Feature disables are defense in depth, not containment: Codex's default exec surface remains available even when shell feature variants are disabled. Hive therefore replaces legacy disk-readable `read-only` with a final permission profile granting only `:minimal` platform reads, no repository/operator path, and no tool network; it selects the native Windows unelevated backend explicitly, and never permits approval escalation. Missing Linux/macOS kernel sandbox support or a Windows restricted-read request fails closed rather than falling back to host reads.
- Before Health remembers a one-shot attestation, the exact sealed binary must pass a deterministic, no-model `codex sandbox` probe. A copied Hive child under a separately granted `bin/` root attempts to read and overwrite random sentinels in an ungranted sibling and connect to a live loopback listener; the parent verifies unchanged bytes and no accepted connection. Parser terminators such as raw `--` are forbidden in operator Prefix values. Release publication separately requires authenticated structured JSONL tests on every shipped OS, with actual command events for denied read/write/network attempts plus the independent random-nonce test.
- Untrusted target code is never given Hive's lifecycle credential. Trusted writes happen only after the hosted evidence boundary.

## Evidence and lifecycle defenses

Hive rejects expired, tampered, partial/non-authoritative, stale-run, cross-repository, and replay-collision bundles. It rejects symlinked, oversized, secret-bearing, absolute, and traversal paths. A partial or changed-files scan cannot close a finding. Closure requires a successful complete target-branch run at the verified merge descendant that evaluated the affected contract and observed the finding absent. A repository-test finding additionally requires the complete canonical GitHub job set: a failed command job may open or preserve the finding only when required Visual jobs succeeded, while closure requires every configured command job to succeed.

One repository-scoped fingerprint maps to one durable bead, issue, active repair branch, and PR. A public marker is never sufficient ownership proof: issue discovery and update require the immutable original author to equal Hive's authenticated writer, and PR discovery requires the target repository's positive ID/full name on both head and base plus the exact branch, head, base, and marker. Foreign marker preclaims are ignored rather than adopted or allowed to block setup; conflicting target-repository claims fail closed. Duplicate delivery is idempotent. Recurrence reopens the same issue and bead. Exact-head checks, required branch protection, file/risk allowlists, retry budgets, pause/kill state, baseline review, and forbidden change classes are all merge prerequisites. Auto-created protection requires `visual-hive` from the exact GitHub Actions App ID resolved from the active GitHub API. Before treating it as a PR verdict, Hive resolves the selected Check Run's Check Suite back to the exact `.github/workflows/visual-hive-pr.yml` workflow, requires event `pull_request` and the exact PR head, and checks the PR/head/base association whenever GitHub returns it. Therefore the green production eligibility seed, a manual same-name check, a wrong workflow, or the same context from another App cannot mask a red or missing PR workflow check. Classic protection and applicable rulesets are evaluated together; any unproven bypass actor or unsupported rule semantics disables autonomous merge. Durable `protection-activation.json` binds the installed policy, trusted production workflow path/event/run/head, production and seed Check Runs, and App ID; repeated runs reverify live protection without another mutation.

A path-allowlist exception is never a generic merge override. Approval uses a read-only plan followed by apply, is serialized with production runs, live-bound to repository identity, audited before activation, explicitly revocable, and invalidated by any base/head/raw-diff change. Every merge, including a normally safe test-only repair, receives a durable intent containing the exact allowed decision, policy snapshot, authenticated writer, strict-protection gate, and authorization digest before Hive calls GitHub. After that intent is durably persisted, Hive performs a second complete gate and raw-diff read, requires exact equivalence, reauthorizes, and only then issues the conditional merge. Recovery validates the persisted pre-merge authority plus live merged PR/head/diff/writer; mutable post-merge checks cannot strand a completed authorized merge, and a direct external merge is denied.

## Emergency response

Run `hive pause --json` to dispatch a serialized hosted control operation that durably denies lifecycle writes while preserving the managed cadence and signed state. `hive stop --json` uses the same hosted pause boundary; it does not attempt to terminate GitHub's scheduler. Use `hive resume --json` only after status proves the active run and state branch are reconciled. Revoke or replace repository credentials through GitHub if compromise is suspected; Hive will not rotate an existing secret. Preserve the state branch, `integrated/audit.jsonl`, lifecycle state, and repair state for review. In explicit local mode also preserve `daemon.log`. Do not edit or delete state until reconciliation is complete.
