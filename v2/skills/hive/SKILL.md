# Hive

Use Hive's MCP tools as the control plane. Keep coverage depth separate from GitHub write authority and take setup through a verified hosted run when the user asks for production setup.

Before changing the Hive/Visual Hive architecture, read the normative
[`visual-hive-integration-contract.md`](../../docs/visual-hive-integration-contract.md).
It controls ownership, packet admission, coexistence, and release-readiness gates.

## Setup workflow

1. Identify the `owner/repository`. Never request a pasted token; use the user's existing GitHub authorization flow.
2. Call `hive_setup_plan` before any mutation. Show detected stack, test layers, files, hosted cadence/state branch, warnings, and required permissions in plain language. New installations default to hosted GitHub Actions execution; use `runtime: local` only when explicitly requested. Linux `bubblewrap`/AppArmor host changes apply only to local repair execution, require system-administrator approval, and must never disable the host-wide user-namespace restriction.
3. If absent, ask for exactly two choices:
   - Coverage: `essential`, `standard`, `comprehensive`, or `custom`.
   - Automation: `advisory`, `issues`, `repair-pr`, or `auto-merge`.
4. Explain that `advisory` persists findings/beads without GitHub lifecycle writes; `issues` can open/update/reopen/close findings but cannot create a branch; `repair-pr` is the open-PRs-only level and can create and revise one linked PR but cannot merge; `auto-merge` can merge only after exact-SHA deterministic, required-check, protection, risk, and hold gates all pass.
5. Obtain explicit setup approval, then call `hive_setup_apply` with the same reviewed values. Let Hive choose its isolated bootstrap state directory unless the user explicitly supplied `state_dir`. Hosted setup creates one signed state branch and create-only authentication secret. For `repair-pr`/`auto-merge`, make `OPENAI_API_KEY` available to setup only when the fixed-name Actions secret is absent; Hive never reads or rotates an existing secret. `advisory`/`issues` need no provider secret.
6. Report the one setup PR. If its newly introduced repository plan exposes a pre-existing failure, require Hive's exact out-of-band `hive/setup-authorized/<binding-sha256>` status; PR author/body/marker text is not setup authority. If the user authorized taking setup to production, wait for hosted checks, merge it only when green and reviewable, then continue. Setup never mutates protection before this merge.
7. After the setup PR merges, continue `hive_run` (or let the managed `schedule` cadence run) through hosted Linux baseline capture. The bootstrap computer is no longer required and no local scheduler should exist. Local setup must not execute target dependency/build/server/browser commands. When status reports `setup_baseline.phase=pr_open`, call `hive_plan_baseline_approval`, show every candidate PNG plus exact run/artifact/PR/head/base/diff/candidate/actor binding, and obtain explicit visual approval. Call `hive_approve_baseline` with every returned value and an accountable reason. Never use generic merge approval or merge it directly. Hive may bootstrap this candidate-only PR before protection only when GitHub proves protection/rulesets are truly absent and the exact GitHub-Actions-App `.github/workflows/visual-hive-pr.yml`/`pull_request`/current-head check is green. Any configured policy must already be strict, no-bypass/admin-enforced, mergeable at the current base, and have all required checks green.
8. Continue `hive_run` through the complete post-baseline production verification. Only a later run may verify installed files and exact production workflow path/event/head; derive repository-test results from the exact GitHub runner-owned job and command-step topology, never target-written ledgers; complete the independent production verdict and actively guarded PR-context eligibility seed; and durably activate exact GitHub-Actions-App-bound `visual-hive` protection before applying evidence or making any lifecycle write. Repository-owned policy is never replaced. A green seed or same-name check is not a PR verdict.
9. Call `hive_doctor`, resolve every failed check, and verify `production_ready=true`. Verify the hosted run, provenance-bound evidence, lifecycle mutations allowed by the selected authority, and duplicate-free durable state. End with `hive_status`.

## Operating rules

- Use `hive_status` before changing an existing installation.
- Use `hive_set_coverage` only for test depth. Use `hive_set_automation` only for issue/PR/merge authority.
- Coverage, automation, and limit tools create or reuse the managed setup PR when repository files must change. Wait for exact-head checks and merge that PR before expecting doctor or production runs to pass.
- Auto-merge path and risk policy is visible in setup plans and configurable through repeatable CLI `--auto-merge-path` / `--auto-merge-risk` flags or MCP setup `auto_merge_paths` / `auto_merge_risks` arrays. Omission preserves installed policy; never broaden these defaults merely to make a trial finish.
- Use `hive_pause` immediately when the user requests a stop or when an unexpected write occurs. In hosted mode it dispatches a serialized controller operation that durably denies lifecycle writes while retaining signed state and managed cadence; it does not stop a local process. Confirm status before `hive_resume`.
- Treat policy denial as a real stop. Never silently downgrade a denied issue, PR, close, reopen, or merge into advice.
- Keep Hive as the only GitHub lifecycle writer in integrated mode. Do not enable Visual Hive's standalone publishers concurrently.
- Treat repository-owned PR workflow source as a trust limitation: exact App/path/event/head provenance does not attest candidate workflow semantics. Hive refuses autonomous workflow changes, but humans can merge outside Hive. Require independent code-owner review and strict no-bypass branch/ruleset protection for workflow and Hive-policy paths; if the repository cannot enforce that, do not select `auto-merge`.
- Never close a finding because a partial, stale, changed-files-only, expired, or unrelated scan omitted it. Closure requires an authoritative target-branch run that evaluated the affected contract after the recorded merge.
- For `repair-pr`, leave the issue open until post-merge verification. For `auto-merge`, require all gates returned by Hive; do not merge separately with a GitHub command.
- For a `merge_policy` path hold, review the exact diff, call `hive_plan_merge_approval` with the PR number and exact head, then repeat its exact base SHA and raw-diff digest in `hive_approve_merge` with an accountable reason. Hive must perform the merge. Never use a direct GitHub merge as a substitute. Use `hive_revoke_merge_approval` if the review is withdrawn.
- Treat `setup_baseline` status as a blocking production state, not advisory output. Resume `pending`, `dispatched`, `artifact_verified`, `proposal_prepared`, `approved`, or `merged` with `hive_run`; for `pr_open`, use only the exact baseline plan/apply tools. A `pending_audit` receipt is still blocking even when the recorded phase is `production_verified`; retry the exact command rather than bypassing it. Head drift triggers a hosted recapture, and a prior approval may be reused only when the complete candidate digest/list and current target tree are identical. `hive_doctor` must remain not ready until full post-merge production verification and its audit receipt are durable.
- If `hive_status` reports `setup_baseline_rebind`, a coverage/setup/Visual Hive change is durably retiring an obsolete capture, PR/ref, or dispatch. Production must remain blocked. Run only its exact `next_command`; the target is immutable, so a different setup request must wait until this transaction completes. Repeated exact setup is the idempotent recovery path. Never edit or delete the rebind or baseline JSON. The checkpoint clears only after the matching changed setup and replacement baseline intent are durable.
- For a resumable infrastructure or patch-engine failure, read the exact recurrence, attempt, failure class, failure ID, reason template, and next-command template from `hive_status`, correct the cause, and call `hive_retry_repair`. Never fabricate or omit the failure ID. If `required_reason_attestation` is nonempty, review the historical patch provenance and retain that exact token inside the accountable reason; Hive denies a missing or changed token.
- If `hive_status` reports `workflow_dispatch_recovery`, do not rerun, delete state, or invent a digest. Use `hive_plan_dispatch_recovery` with the exact correlation. Prefer `revoke` whenever the original request might still arrive; use `retry` only with independent evidence that it was not accepted. Repeat every exact value from the plan in `hive_recover_dispatch` with an accountable reason.
- Use `hive_upgrade` and `hive_rollback` only with immutable 40-character Visual Hive commit SHAs. Review the generated PR. For an integrated hosted release change, install the signed candidate and repeat setup so the managed workflow records the exact current release and one exact predecessor. A fresh runner may restore only those identities and checkpoints under the current one. Never force an older binary onto newer state; schema/release rejection is a fail-closed rollback boundary.
- Use `hive_transfer_setup_authorizer` for a planned maintainer handoff. It must be initiated by the recorded old numeric actor; report its exact PR, `next_command`, and pre-merge `cancel_command`. Never edit its intent or substitute a manually posted status. After merge, finalize only through the reported command. If the old actor is lost before authorization, stop and use the documented repository-admin remove/archive/fresh-install break glass rather than forging a rotation.
- Use `hive_uninstall` only after explicit confirmation. Uninstall first drains hosted baseline state: capture-only state is audited away; an open baseline PR/ref is closed/retired only under exact repository/PR/URL/marker/head-or-descendant/base/diff evidence; a merged baseline is accepted only with Hive's durable exact merge authority. Any ambiguity remains paused for retry. Uninstall is otherwise two phase: preparation runs Hive's bounded exact issue/PR/branch cancellation drain, always preserves state, and returns `finalization_pending`, `next_command`, and a pre-merge `cancel_command`; run finalization only after the exact cleanup PR merges. If strict-base or head drift invalidates the cleanup, use `cancel: true` alone. Permanent deletion repeats quiescence and exact PR/target/protection reconciliation and must fail closed on any mismatch. Hive never deletes or rewrites a whole protection policy during uninstall; remove only the exact `visual-hive` required context, preserve unrelated settings, and retry.

## Tool fallback

If Hive MCP tools are unavailable but the CLI is installed, use `hive` when it is on `PATH`; otherwise use the installer's exact launcher (`$HOME/.local/bin/hive` on Linux or `$env:LOCALAPPDATA\Hive\hive.exe` on Windows). Run the equivalent CLI with `--json`. Each `--json` invocation must emit exactly one parseable UTF-8 JSON document on stdout; parse the whole stream and use the exit code, never scrape mixed human output. Hive automatically selects isolated per-repository bootstrap state; preserve an explicit `--state-dir` only when the user supplied one. Hosted `run`/`start`/`stop`/`pause`/`resume` dispatch the repository controller and do not create a local scheduler. Start with:

```text
hive setup --repo OWNER/REPO --coverage LEVEL --automation MODE --provider codex --visual-hive --start --json
hive run --json
hive doctor --json
hive status --json
```

Do not ask the user to hand-edit workflow YAML or repository variables. If neither MCP nor the CLI is available, report the missing installation rather than improvising repository writes.
