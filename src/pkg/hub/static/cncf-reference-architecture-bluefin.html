Project Bluefin: a bootc desktop OS built and maintained by a governed agent fleet

A cloud-native desktop operating system delivered as bootable OCI container images - assembled by a container build pipeline, signed with Sigstore, verified on the client by a default-deny policy, updated in place with bootc, and produced by repositories maintained under an explicit autonomy model.

02 Describe your organisation

Project Bluefin is a community-run desktop operating system in the Universal Blue family, distributed as bootable container images rather than as a package set. It is maintained by volunteers across 54 repositories in the projectbluefin organization and a wider ecosystem of 140 repositories in ublue-os. Images ship weekly on a Tuesday cadence; 222 releases have been published to date, and Fedora countme telemetry estimates roughly 4,100 active installations.

The project has no commercial entity behind it. Its scarcest resource is maintainer attention, and that constraint is what shapes both halves of this architecture: the build side minimizes the surface a human must inspect, and the maintenance side delegates mechanical work to agents under enforced limits.

03 Brief overview of the architecture

There are two coupled systems.

The delivery architecture turns a declarative image definition into a signed OCI artifact that a user's machine boots and updates atomically. The unit of delivery is a container image; there is no package-by-package upgrade path on the client, and layering packages onto a running system is actively discouraged by the update tooling.

The maintenance architecture keeps the repositories that produce that image healthy. A fleet of AI coding agents triages issues, writes fixes, reviews pull requests and keeps CI green, under an autonomy model that determines what each agent is permitted to do and enforces it below the level of the prompt.

The connecting principle is that both halves answer the same question: when something lands in a public artifact that other people boot, who is accountable for it and how is that checkable afterwards.

04 The delivery architecture

Build

An image is assembled by a single Containerfile with a strict composition order. Three inputs are pulled by digest: a shared common layer, a Homebrew layer, and a digest-pinned Fedora Silverblue base. A scratch stage overlays build scripts and system files in defined precedence, so that image-specific files deliberately land last and win. All mutation happens in one RUN with cache mounts and a build secret, invoking an ordered pipeline: package installation, kernel modules, desktop extensions, cleanup, initramfs regeneration, repository validation and tests. The final instruction is bootc container lint.

One supply-chain control inside that pipeline is worth naming, because it is a pattern other projects can copy directly. Packages are split into Fedora packages and COPR packages. Fedora packages install first in bulk; COPR packages install individually with isolated repository enablement, explicitly to prevent a malicious third-party repository from shadowing a distribution package with a forged version. Third-party repositories for Docker, VS Code and Tailscale are added and then immediately disabled, enabled only for the single transaction that needs them, and a validation step refuses to commit an image with a repository left enabled.

Rechunk

Before publication the image is passed through a pinned rechunker, which reorganizes layers so that incremental updates transfer less data. This is where OCI and bootc labels are applied. It is a distinct pipeline stage and a deliberate cost: build time is spent so that every user's update is smaller.

Sign, attest, publish

Images are pushed to GHCR and signed by digest with cosign. A software bill of materials is generated with Syft, attached to the image as an OCI referrer using ORAS, and then itself signed. Build provenance is attested and pushed to the registry. Signing the attestation as well as the artifact is not common practice and is worth highlighting.

Two build lines exist and differ here, which matters to anyone copying this pattern:

  • ublue-os/bluefin, the mature line, signs with a key, holding a private key in CI and shipping the public key in the repository. Keyless signing is explicitly disabled.
  • projectbluefin/bluefin, the newer line, signs keyless through OIDC, holds no signing secret, and resolves its base image only after a cosign verification. It also adds Trivy CVE scanning and SLSA Build L2 provenance.

The newer line is the direction of travel. Both are documented rather than one being presented as the whole story.

Verify on the client

This is the strongest property of the architecture and the one most often missing elsewhere. Verification is not advisory and does not depend on the user running a tool. The image ships a container policy whose default is reject, with the project's registry namespace requiring Sigstore-signed images matched to the repository, validated against public keys shipped at a known path in the image. Fulcio and Rekor roots are physically present in the image, so verification does not require reaching a network service at boot. Signature verification is performed by the container stack's policy engine; the cosign binary itself is deliberately removed from the shipped image.

Secure Boot is handled with a project-enrolled key, verified in CI on every build by extracting the kernel from the built image and checking it against the project's certificates before publication.

An honest limitation to state: the policy's default-deny governs the enumerated registries, while a catch-all entry accepts other registries on the docker transport. The guarantee is strong for the project's own images and should not be described as universal.

Update

A user updates with one command that spans four distinct software sources: the OS image through bootc, system Flatpaks, user Flatpaks and Homebrew. The update path refuses to proceed if it detects packages layered onto the running system, telling the user to reset first, with the explicit reasoning that layering forfeits the project's maintenance guarantee. This is the architectural boundary that makes an image-based OS tractable: the base is immutable and identical across installations, and everything variable lives in layers above it.

Layers above the base

Four mechanisms, each with a defined role, keep the base immutable while giving users a complete system. Flatpak delivers graphical applications through a curated app store with a blocklist, replacing the distribution's default software centre. Homebrew, delivered as an OCI layer composed into the image, delivers command-line tooling through curated bundles, so users never need to layer RPMs. Distrobox, inherited from the upstream base, provides mutable traditional userspaces for development. A ujust verb layer composes all of it into discoverable commands, and a Go desktop application provides a graphical front end over updates, rollback, channel switching and developer mode.

Within that Homebrew layer sits a curated CNCF bundle of 89 formulas spanning graduated, incubating and sandbox projects. It is a distribution decision rather than a runtime dependency: Bluefin makes the cloud native toolchain one command away for a developer workstation, without installing any of it into the OS.

05 The maintenance architecture

The problem

Fifty-four repositories, volunteer maintainers, and a workload dominated by mechanical tasks: triage, reproduction, dependency and base-image currency, CI repair, routine review. Pointing coding agents at those repositories solves the throughput problem and creates an accountability one. In a project whose artifact is an operating system other people boot, an unaccountable automated commit is a supply-chain question.

The solution

Project Bluefin runs a self-managed Hive, an Apache-licensed control layer for fleets of coding agents developed in the KubeStellar organization, a CNCF Sandbox project. Bluefin documents the deployment publicly as its factory.

Three properties make it compatible with the supply-chain posture described above.

Determinism before judgement. Filtering, classification, duplicate detection, merge gating and policy enforcement are handled by inspectable code before any model is invoked. Models are used only where judgement is required.

An autonomy model enforced in code. A six-level maturity model determines both which agent roles exist and what they are physically able to do, from advisory operation with no writes at all, through filing issues, through opening pull requests that carry a hold label a human must remove, up to merging on green CI. Raising the level is an explicit operator decision.

Enforcement below the prompt. Limits are applied through tool denial, scoped short-lived credentials, and a network proxy between every agent and the forge. A write an agent's level does not permit is refused at the wire rather than discouraged in an instruction. If the enforcement path cannot be established at startup, the system refuses to start rather than run unenforced.

The contributor boundary

The most transferable piece is how an agent is isolated. Bluefin packages the contributor runtime as a distroless image run in a KVM microVM where available, falling back to a plain container, with no host home directory mounted and an unprivileged user. Inside that boundary the forge CLI is a wrapper: an assigned task cannot authenticate, cannot issue a mutating API call, and cannot reach any subcommand outside an allowlist. Contributor mode is a root-owned marker the agent cannot forge. Output is labelled with the contributor identity, so every change is attributable.

The authority split is stated explicitly by the project: the orchestrator owns task selection, assignment, prompts, leases and output capture; the agent harness owns execution, model choice and tool boundaries; the appliance owns the isolation boundary and the credentials that cross it.

Scope doctrine

The project constrains what agents may attempt, and this is an architectural decision rather than a policy footnote. In its own words it is a toil-reduction factory, not a feature factory: agents repair what is broken and finish what the project already decided to do, and do not add features, dependencies, configuration surfaces or architecture. Changes are sized to be reviewable rather than complete, on the reasoning that reviewer attention is the scarce resource. Where a task can only be finished by out-of-scope work, the deliverable is a written finding rather than a larger change.

06 Guiding principles

  1. The unit of delivery is a signed image, not a package transaction.
  2. Verification is enforced on the client by default-deny policy, not requested of the user.
  3. The base is immutable; everything variable lives in layers above it.
  4. Automation is granted capability in explicit, revocable steps.
  5. Limits are enforced by infrastructure, not by instructions to a model.
  6. Every change, human or automated, has a named accountable identity.
  7. Reviewer attention is the constraint that sizes the work.

07 What has worked well - and what has not

✓ What has worked well

  • Digest-pinned inputs and a single mutation step make builds reproducible and make a diff of what changed between two images tractable. Client-side default-deny verification means a compromised registry path does not become a compromised fleet. Rechunking pays build time once to reduce every user's update. Splitting distribution packages from third-party repositories, and enabling those repositories only transactionally, closes a shadowing attack that is easy to miss.
  • On the maintenance side, the autonomy model has allowed agents to carry substantial throughput while leaving the project's review and CI guarantees intact. Several hundred agent-authored pull requests have merged across the organization, all publicly attributable to a single named identity, none bypassing the gates a human contribution passes.

✗ What has not worked well

  • Memory limits on hosted runners forced the SBOM step to export a container root filesystem and scan a directory rather than scanning the image directly, which is slower and less elegant than intended. Registry digest behaviour required pushing twice so that signing by digest is correct. Two build lines with different signing models coexist, which is a transitional cost. rpm-ostree remains in the pipeline as the rechunking mechanism even though the delivery model has moved to bootc, and an OCI-native replacement is being developed to remove it.
  • On the maintenance side, the terminology between the orchestration layer and the contributor appliance has diverged, with two different role vocabularies in current documentation. Public outcome metrics for the factory are not yet durably published; the live queue widget is not a substitute.

08 What glue has been required

A just recipe layer functions as the build DSL and is reused by both CI and contributors. A wrapper over it provides the user-facing verb layer with shell completions. The Homebrew layer is packaged as an OCI image so it can be composed into the build rather than installed at runtime. The contributor appliance is entirely glue by nature: it exists to hold an isolation boundary and a credential contract between an upstream orchestrator and an agent harness that neither side owns.

09 How the architecture has evolved

The delivery model moved from package-based updates to image-based delivery, then from ostree-native tooling to bootc as the lifecycle interface, with rpm-ostree surviving only as chunking machinery. Signing moved from key-based to keyless in the newer line, removing a CI secret entirely. Supply-chain posture accreted in stages: signing, then SBOM, then attaching and signing the SBOM, then provenance attestation, then CVE scanning.

The maintenance architecture is the newest layer. It began as agents with credentials and evolved into agents with none, where capability is granted by a maturity level and enforced at the network boundary, and where the interesting engineering is the isolation contract rather than the prompts.

10 What is next

Completing the migration to OCI-native rechunking and retiring rpm-ostree from the pipeline. Converging the two build lines on keyless signing. Extending CVE scanning and SLSA provenance across both. Publishing durable factory metrics. Reconciling the role vocabularies between orchestrator and appliance.

11 Verification notes

Every architectural claim above is drawn from public sources: the Containerfiles, build scripts and workflows in ublue-os/bluefin and projectbluefin/*, the shipped policy and OpenTelemetry configuration in projectbluefin/common, and docs.projectbluefin.io. Agent throughput is independently checkable on GitHub by querying merged pull requests authored by the orchestrator's app identity.

Three things are deliberately not claimed. The factory's exact repository coverage is described by the project as the whole formation but is not enumerated here. A frequently cited 81 percent pull-request acceptance figure belongs to KubeStellar, not to Project Bluefin, and is not presented as a Bluefin outcome.
