02 Describe your organisation

KubeStellar Console is an open-source, Apache-licensed dashboard for operating many Kubernetes clusters at once, created in January 2026. In roughly eight months it has published 234 releases on a nightly-plus-weekly cadence, accumulated 84 contributors, and closed over eleven thousand issues.

It is a repository inside the KubeStellar organization, which CNCF accepted as a Sandbox project in December 2023. Console is not separately listed in the CNCF landscape and inherits standing through that organization; the project reports to CLOMonitor under KubeStellar.

An honest statement of adoption: the project's adopters file lists thirteen entries, and they are overwhelmingly CNCF projects that accepted a guided install mission rather than organizations running Console in production. The production adopter tier is empty. The interesting claim in this document is therefore not about deployment scale. It is about how the software is made.

03 Brief overview of the architecture

Console has three runtime pieces and an unusual fourth: the system that maintains it.

A Go backend built on Fiber serves an API, holds state in an embedded CGO-free SQLite database, authenticates through GitHub OAuth, and talks to clusters with client-go. A React and TypeScript frontend built with Vite provides the dashboard. A local agent runs on the operator's own machine, discovers kubeconfig contexts, and forwards requests to each cluster's API server, authenticated with a shared bearer token.

The multi-cluster model is flat and is Console's own. It fans out across the contexts in an operator's kubeconfig, talks to each cluster's API server directly, and labels what it deploys with its own management label. It defines its own custom resources for cluster groups, managed workloads and workload deployments.

To be explicit, because the shared organization name invites the assumption: Console is not a user interface for the KubeStellar controller and does not depend on KubeStellar's placement model. It is a dashboard for operating Kubernetes clusters, whichever way those clusters are managed. The two are sibling projects in one organization, not two halves of one system.

04 Deployment topology

Six supported modes, which is itself an architectural position: meet the operator where they are rather than requiring a cluster to evaluate a cluster tool.

The hosted demo runs on Netlify, where supported API routes are served by Netlify Functions rather than the Go backend. This is worth stating plainly because it surprises people: the public Console and the self-hosted Console share a frontend and diverge behind it, and the functions directory is maintained as a production mirror of the corresponding Go handlers.

Self-hosted modes run the real backend: prebuilt binaries with the local agent, an OAuth variant, a container image, kubectl apply, and a Helm chart. The chart is hardened in ways worth copying: network policy, pod disruption budget, a database backup CronJob, a pre-upgrade volume migration hook running as a numeric non-root user, a values schema, restricted pod security context, and OpenShift route support.

The two postures differ in where trust sits. Run outside the cluster, Console holds the operator's kubeconfig and the local agent is the boundary. Run inside, it holds a ServiceAccount whose default is read-only cluster access with namespace creation off by default.

05 The maintenance architecture

This is the part of the system that makes it a reference architecture rather than a dashboard.

Scale of machine authorship

Of 10,276 merged pull requests, 3,229 were authored by the Hive app identity, about 31 percent overall. The bot is the second-highest contributor by commit count in the repository's history. In the most recent 200 merged pull requests, 139 were Hive, 53 were dependency automation, seven were CI, and one was directly human-authored.

That last number is the one to sit with. At current cadence, nearly all code entering this repository is written by machines, and the architecture exists to make that safe rather than to make it fast.

Authorization is a gate, not a setting

Agent automation is reachable by mention, and every mention passes through a reusable trust gate workflow that evaluates the actor against repository and organization membership and returns a trust decision with a reason. Untrusted actors cannot trigger automation. The bot announces this behaviour on every human-opened issue, so the boundary is discoverable rather than hidden.

Work is queued by label, and the label vocabulary is the state machine: requested, processing, complete, queued, stalled, draft, ready, active, retry counts, and the one that matters most, a label meaning a human decision is required rather than more automation.

Advisory mode

Agents do not begin with write access. At lower levels of the maturity model they run in advisory mode: they analyze the codebase and pipeline continuously and post findings, tagged by severity, to a living advisory issue, without opening pull requests or filing issues. The repository keeps these advisory reports as documents. Capability is earned in explicit steps rather than granted at once.

Every change passes the same gates

The project states the rule directly: all pull requests, regardless of origin, pass the same quality gates. Those gates are unusually dense, and several exist specifically because the authors are machines. Alongside the expected build, typecheck, unit, end-to-end, accessibility, visual regression, CodeQL and DCO checks, there are ratcheted detectors for AI antipatterns, each with a recorded baseline that may only decrease: raw hex colours, non-localized strings, inline style colours, raw font sizes. Coverage is ratcheted per package. Lint carries a frozen baseline. There is a nil-safety gate and an API contract check.

A ratchet is the right primitive here. It does not demand that a large codebase be clean today; it makes it impossible for automation to make things worse while allowing any change that improves them.

Attribution and scrutiny tiers

A workflow labels pull requests as AI-generated based on author type and commit trailers, explicitly to satisfy an audit-trail criterion of the maturity model, so that human and machine authorship can be told apart later. Every pull request also receives exactly one scrutiny tier on open, with the lowest tier reserved for lockfiles, checksums, documentation and generated snapshots.

Tool neutrality

The repository carries instruction files for many agent tools and designates one canonical guide, stating that where a tool-specific file conflicts, the canonical one wins. The orchestration layer is likewise backend-neutral. This matters for longevity: the governance survives a change of model vendor.

06 Guiding principles

  1. Machine authorship is normal; unreviewed machine authorship is not.
  2. Authorization to trigger automation is evaluated, not assumed.
  3. Capability is granted in steps, beginning with advice and no write access.
  4. One quality bar, applied identically to human and machine contributions.
  5. Ratchets, not absolutes, so automation can never regress a metric.
  6. Authorship is labelled at merge time so the audit trail survives.
  7. The canonical instruction file wins, so tool sprawl cannot fork the rules.

07 What has worked well - and what has not

✓ What has worked well

  • The ratcheted gates have let a small human team accept a very high volume of machine-authored change without the codebase degrading, because the failure mode of automation at scale is not a dramatic bad commit but slow erosion, and a ratchet is precisely the instrument against erosion.
  • The trust gate has made automation safe to expose publicly. The bot can be mentioned by anyone, and the gate rather than obscurity is what prevents misuse.
  • Advisory mode has proven valuable beyond its role as a training wheel: continuous analysis posted to a living document is useful even where write access is never granted.

✗ What has not worked well

  • Two agent instruction sets in the repository currently contradict each other on whether to build and lint locally, one forbidding it and the other calling it the most important rule. When instructions are the interface to your contributors, contradictions are defects.
  • Published counts of the install-mission catalogue disagree across the readme, the chart annotation and the upstream project readme. The bot is referred to by two different names in different places. The architecture document in the repository names a frontend version the code has moved past.
  • Some declared resource types in the tree imply a coupling to KubeStellar placement that Console does not actually have, which invites exactly the misreading this document corrects. Removing them would make the boundary obvious from the code rather than from prose.
  • Software bills of materials are not generated for releases, although signing and provenance attestation are. That is a gap relative to the companion Bluefin architecture, which does generate, attach and sign them.

08 What glue has been required

The local agent is the central piece of glue: a small daemon that exists because a browser cannot hold a kubeconfig or reach an API server directly, bridging browser-based and command-line tooling. The Netlify function mirror is glue of a less comfortable kind, a second implementation of a subset of the backend maintained in parallel for the hosted path. The ratchet baseline files are glue between a large existing codebase and a standard it does not yet meet.

09 How the architecture has evolved

The maintenance architecture arrived after the system and reshaped it. Gates that began as ordinary continuous integration grew a second purpose as the boundary of machine autonomy. Labels grew from triage aids into a state machine driving automation. Attribution grew from a courtesy into an audit requirement. Agent capability moved from advisory analysis to authorized pull requests under a maturity model rather than being granted at once.

10 What is next

Reconciling the contradictory agent instruction sets and the inconsistent counts and bot naming. Removing the unused resource declarations that imply a coupling Console does not have. Adding SBOM generation to releases. Reducing the ratchet baselines rather than merely holding them. Recording a production adopter, which would turn a strong engineering story into a strong adoption one.

11 Verification notes

Every claim above is checkable in public sources: the repository's manifests, workflows, chart and documentation, and the GitHub API. Agent throughput can be reproduced by querying merged pull requests authored by the orchestrator's app identity against total merged pull requests.

Three things are deliberately not claimed. Console is not the user interface of the KubeStellar controller and is not presented as one; it is a sibling project with its own multi-cluster model. No production adopter is claimed, because the adopters file lists none. OpenTelemetry is named as a dependency rather than a capability, because no instrumentation was found.
