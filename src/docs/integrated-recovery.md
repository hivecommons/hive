# Integrated Hive Recovery and Troubleshooting

## Hosted controller recovery

New installations default to the hosted runtime. `hive setup --start` installs one managed `Hive Hosted Controller` workflow with both an exact cron `schedule` and `workflow_dispatch`; it does not create a local process, systemd unit, or Windows task. GitHub Actions concurrency permits only one controller operation at a time. The bootstrap computer can be shut down after the setup PR merges.

Durable state is stored as one bounded, canonical `hive.hosted-state.v1` bundle on the dedicated `hive/state-<repository-id>` branch. `HIVE_HOSTED_STATE_KEY` is a create-only repository Actions secret containing the HMAC-SHA256 key. Each fresh runner verifies the exact repository, state branch, release, workflow path, signed parent sequence, regular-file inventory, and remote branch head before restoring state. Every mutation checkpoint creates the exact next-parent commit and advances the branch with compare-and-swap; overlap, ancestry drift, malformed state, or a changed remote head fails closed.

After an interruption or bootstrap-host shutdown, run:

```bash
hive status --json
hive doctor --json
```

Hosted status verifies the exact managed workflow bytes, state branch and secret metadata, controller run identities, lack of overlap, latest completed cycle, freshness, and current default-branch head. `hive run --json` dispatches an immediate cycle; `hive pause --json`, `hive resume --json`, and the supported recovery command dispatch exact idempotent controller operations. Rerunning the same request reconciles its request ledger instead of duplicating lifecycle records. Never edit `state.json`, force-push the state branch, or replace either repository secret.

For hosted `repair-pr` and `auto-merge`, setup also provisions `OPENAI_API_KEY` as a create-only repository Actions secret. If it already exists Hive uses only its metadata and never reads or rotates it. If it is absent, rerun setup with `OPENAI_API_KEY` present only in the setup process. `advisory` and `issues` do not require this provider secret.

## Local runtime compatibility

Existing local installations remain local unless setup explicitly changes `--runtime`. Local Visual Hive `repair-pr`/`auto-merge` is owned by the existing ordinary Hive/dashboard process: configure that process with the setup's exact `HIVE_STATE_DIR`, keep the repository in its normal project scope, and require its existing dashboard listener to become HTTP-ready. After setup succeeds, the running dashboard automatically reconciles and activates the installed contract without a restart. Do not use `hive run` or `hive start` for normal operation in this mode. Use `hive stop` only when status or doctor directs cleanup of a stale legacy scheduler; it does not stop ordinary Hive/dashboard. Local `advisory`/`issues` retains the legacy per-user scheduler: on Linux it requires systemd/logind and exact `Linger=yes`, and on Windows it uses a least-privilege `InteractiveToken` task that resumes only after user logon. For that legacy mode, `hive start --json` is an idempotent service repair and concurrent starts converge on the OS-held lease. All local modes use the owning process account's GitHub and, when repairs are enabled, Codex credential stores. These requirements do not apply to hosted installations.

## Common doctor failures

- `visual_hive_runtime`: reinstall the signed integrated release matching the configured exact Visual Hive commit. Do not point Hive at a mutable branch.
- `provider`: for hosted `repair-pr`/`auto-merge`, confirm the create-only `OPENAI_API_KEY` Actions secret exists; for local mode, run the provider login in the scheduler-owning account.
- `github_auth`: run `gh auth status`, then `gh auth login` if needed. Confirm access to the exact target repository.
- `setup_installed`: review and merge the single Hive setup/upgrade PR after checks pass. A stale historical PR is ignored only when the exact durable policy is already installed on the target branch.
- `workflow_installed`: rerun idempotent `hive setup` and inspect the setup PR.
- `setup_baseline_state`: run `hive status --json` and follow its exact `setup_baseline.next_command`. `pending`, `dispatched`, `artifact_verified`, and `proposal_prepared` are restart-safe hosted-capture/proposal phases; `proposal_prepared` means the exact branch and commit are durable before push/PR creation. `pr_open` requires `hive approve-baseline --plan --json`, visual review of every candidate PNG, and the complete returned apply binding; `approved` means Hive will retry only the same exact merge; `merged` requires one complete trusted post-merge production verification. A phase with `pending_audit` remains blocked even if its phase text says `production_verified`; retry the reported command so Hive writes the exact idempotent audit receipt. Never copy PNGs from a local browser, edit the intent, use generic repair approval, or merge the held baseline PR outside Hive.
- `branch_protection`: before the setup PR is merged, doctor reports setup activation pending and remains read-only. After merge, the next trusted hosted cycle verifies the exact production workflow path/event/default head, completes `visual-hive-production` plus the actively guarded `visual-hive` eligibility seed, and activates strict/up-to-date protection with the PR `visual-hive` context bound to the exact GitHub Actions App ID. If protection is absent, run `hive run`; the scheduled controller continues after that cycle. If repository-owned policy exists but is missing strict mode, administrator enforcement, or the exact App identity, update that policy explicitly because Hive will not replace it. A green production seed never counts as a PR verdict; Hive requires exact `.github/workflows/visual-hive-pr.yml`/`pull_request`/PR-head Check Suite provenance at merge time.
- `hosted_controller_workflow`, `hosted_state_branch`, `hosted_state_secret`, `hosted_controller_identity`, `hosted_controller_overlap`, `hosted_latest_cycle_success`, `hosted_latest_cycle_fresh`, or `hosted_latest_cycle_head`: do not start a local scheduler or edit the managed workflow/state. Use `hive status --json` to inspect the exact mismatch. Restore the exact setup PR bytes, permissions, or release identity and run the supported hosted operation again. A stale cycle may be refreshed with `hive run --json`; overlap or identity drift must be reconciled before lifecycle writes resume.
- `workflow_dispatch_state`: run `hive status --json` and use its exact dispatch-recovery plan. Do not dispatch another run or delete the checkpoint.
- `lifecycle_state` or `repair_state`: run `hive pause --json`, preserve the reported state directory and error, and correct the underlying filesystem/backup problem before retrying doctor. Hive recovers supported torn writes and schema migrations itself; never hand-edit or delete lifecycle, repair, audit, journal, or hidden-ref state to force readiness.

## Setup authorization recovery

When a managed setup, upgrade, rollback, cleanup, or authorizer-transfer PR changes after Hive authorized it, the old `hive/setup-authorized/<binding-sha256>` status is intentionally unusable. Do not copy a context, post a replacement status manually, edit the PR body, or weaken the required check. Rerun the corresponding Hive command. Hive re-resolves the authenticated numeric human actor, the exact PAT or App-bot writer, App/installation identity where applicable, exact PR/base/head, canonical diff and blobs, required-present and required-absent paths, then creates and reads back the status for the new immutable binding. A substantive management change requires the recorded numeric authorizer; a true no-op preserves the installed binding.

For a planned handoff, authenticate as the currently recorded authorizer and run `hive transfer-setup-authorizer --new-authorizer NEXT_LOGIN --reason "ACCOUNTABLE_REASON" --json` (MCP: `hive_transfer_setup_authorizer`). Hive resolves the proposed login to an exact numeric human GitHub `User`, persists an interruption-safe old/new/base/head/diff/PR/status intent, and opens one dedicated reviewable managed PR. The old actor creates its exact authorization status and remains the local authority while the PR is open. All competing setup, management, production, approval, retry, recovery, and resume mutations fail closed. After the exact PR merges, run the `next_command` from status; either the old actor or the explicitly designated new actor may finalize, but Hive switches local authority only after re-verifying the latest old-actor status, exact merged PR, and complete managed bytes at the current default head.

Before merge, the old actor can use the reported `cancel_command`. Cancellation re-reads the exact repository ID, PR number and URL, transaction-unique marker, same-repository managed head branch, and base branch; refuses a merged PR; closes only that exact open PR; and deletes the ref only when its current head is the recorded Hive commit or a proven descendant created by a strict-base/update-branch operation. Base/head SHA drift is therefore recoverable without weakening finalization. Every step is audited and restart-safe after a partial API failure, the intent is removed only after exact ref retirement, and the old Config authority remains unchanged. A restarted transfer gets a fresh marker and cannot collide with the cancelled PR. Never delete the intent JSON or branch manually.

If the old actor is permanently unavailable before a transfer was authorized, Hive deliberately has no software bypass. The repository administrator's break-glass recovery is to stop Hive, preserve the complete local state and audit log, use the repository's independently audited administrator/ruleset process to merge a narrowly reviewed removal of every Hive-managed file and exact `visual-hive` required context, then archive the old state and perform a fresh Hive setup as the new human actor. Restore the repository's no-bypass protection after the fresh setup activation. Do not manually replace only the numeric ID, forge a status, reuse the old state, or treat this emergency reinstall as a normal transfer.

If a setup PR is green despite a pre-existing repository command failure, inspect the `Hive setup authorization` job and confirm its exact-context status targets that PR. The JSON bootstrap proof and target-written TSV are diagnostics only. After merge, production Hive accepts a failed workflow only when exhaustive GitHub job/step evidence contains exactly one terminal job for every configured command and the required Visual jobs succeeded. Missing, duplicate, rerun, or unexpected repository-test jobs are an evidence failure, not a finding. Correct workflow topology or rerun through Hive; never fabricate an artifact ledger.

## Hosted setup-baseline recovery

Hive checkpoints the hosted baseline correlation and target head before dispatch, then binds the exact run and artifact before opening a PR. Rerun `hive run --json` after an ordinary interruption; it resumes the same phase and never substitutes the newest workflow run or opens a second active baseline PR. If the default branch moves before approval, Hive closes only its exact managed PR, retires only its exact/proven-descendant branch, and starts a fresh hosted capture. If it moves after merge but before production verification, Hive recaptures at the new head and can reuse the prior human approval only when the complete candidate list/digest and exact current target tree are identical.

If setup, coverage, or Visual Hive configuration changes while any baseline phase is active, Hive first writes `setup-baseline-rebind.json` with one immutable target and leaves production fail-closed. It polls a known cancellation until the exact capture run is terminal; for a lost dispatch response it exhaustively rediscovers and cancels the exact run when present, then durably tombstones the correlation. It discovers/closes only the exact unmerged baseline PR (including the create-response-lost window), retires only its exact/proven-descendant ref, and removes the dispatch checkpoint only after the tombstone is durable. A crash, audit-write failure, or transient GitHub error leaves a retryable receipt/checkpoint; `hive status --json` and `hive doctor --json` show its one complete `hive setup` command. A changed command cannot replace the target mid-transaction. Never delete or edit either baseline state file. Only a successfully saved matching setup and, when required, its new exact baseline intent consume the `resources_retired` checkpoint.

The approval plan is read-only and binds repository name and immutable ID, numeric setup authorizer, capture run/artifact/head, candidate paths/digest, exact PR URL/number/head/base, and raw-diff digest. Apply must repeat every value and an accountable reason. A changed actor, candidate, artifact extraction, head, base, diff, label, review, mergeability result, check, App, workflow path/event, or required policy invalidates it. The held PR stays held until the complete pre-release gate is green. On a truly unconfigured repository, explicit specialized approval plus the exact green Visual Hive PR provenance is the one-time bootstrap path. If any protection or ruleset exists, weak strict/admin semantics, an unknown bypass, an incomplete required-check inventory, or any non-success required check fails closed; fix repository-owned policy and rerun the same plan/apply rather than deleting state.

After Hive merges, it verifies that the exact candidate tree is on the current default head, dispatches the full production workflow, validates the authoritative evidence bundle, and persists `production_verified`. It deliberately stops once more so a later run performs protection activation and only then permits issue/repair lifecycle writes. `hive doctor --json` remains not ready throughout those phases, while `hive status --json` provides the next command and exact run/PR evidence.

Uninstall drains this state before cleanup. Pending capture-only state is removed with an audit record. An open baseline PR is closed only after exact repository/PR/URL/marker/branch/head/base/diff/candidate verification, and its branch is retired only at the recorded head or a proven descendant. A merged PR is accepted only when the durable Hive merge-attempt and exact merged evidence match. Any ambiguity leaves automation paused and state intact; retry `hive uninstall --json` after correcting the reported mismatch, never delete `setup-baseline.json` manually.

## Failed or interrupted repairs

Use `hive status --json` to inspect the fingerprint, bead, issue, repair attempt, branch, PR, check SHA, validation run, and retry count. Do not delete a repair branch while its PR is open. Hive resumes the existing attempt after restart; a new attempt is created only after a terminal revision decision and within the configured retry budget.

Infrastructure and patch-engine failures pause at an exact durable checkpoint without silently consuming another model attempt. `hive status --json` returns `resumable_repairs` with the recurrence, attempt, failure class, failure ID, `reason_template`, and a shell-safe `next_command_template` that includes `--json`. Replace the descriptive part of the reason with an accountable statement of what was inspected or corrected, while preserving every exact binding in the template, then run it. Model-invalid patches consume a model attempt and are revised normally; they cannot be reclassified into an endless same-patch retry.

An upgraded Hive may exceptionally recover a complete historical read-only Codex patch after proving that an older rejection was caused only by deterministic preparation-tool output. Hive does not invoke the provider again or silently apply that patch. The corresponding `resumable_repairs` item includes a nonempty `required_reason_attestation` such as `attest-historical-read-only-codex:<sha256>`, and its command template already includes that token inside the bounded reason. Review the reported patch digest, replay proof, and provider identity; keep the token verbatim when replacing the descriptive reason. A missing, changed, or truncated attestation is denied and audited.

Preparation and validation commands are now surrounded by durable tool snapshots. Hive restores their generated output, keeps the model base and validated candidate in immutable guarded Git objects, and creates the repair commit from that sealed candidate rather than from mutable post-validation working-tree bytes. If a command or descendant process survives its expected boundary, Hive quarantines the checkpoint as an infrastructure or patch-engine failure and exposes the supported retry path above. Do not delete hidden Hive refs, repair journals, or lifecycle JSON manually.

If GitHub mutation partially succeeded, rerun `hive run --json`. The durable outbox and stable markers reconcile the existing issue/PR instead of creating duplicates. A production workflow dispatch is checkpointed in `integrated/workflow-dispatch.json` before the API call and bound to a random correlation, exact repository/ref/workflow, and the run ID returned by GitHub's current API. Exact-title correlation recovers the run after a crash before that response was persisted and supports older servers that return no run details. Restart recovery waits for that same run; it never substitutes the newest manual run. The checkpoint is removed only after its evidence is successfully consumed, or after an observed terminal failed/cancelled run is handled. An ambiguous transport failure retains the checkpoint and fails closed rather than issuing an uncorrelated duplicate.

### Ambiguous workflow dispatch recovery

When the workflow-dispatch connection fails without an HTTP response, Hive cannot prove whether GitHub accepted the request. The next Hive operation performs one exhaustive, paginated search for the exact workflow, ref, event, and 256-bit correlation. It binds the run if found. If no run is found, it releases the production lease immediately, marks `production_ready=false`, and returns both copy-paste recovery plan commands in `hive status --json`. It does not wait for the normal run timeout and does not dispatch again automatically.

Plan first. Planning is read-only and fails if discovery is incomplete or an exact run exists:

```bash
hive recover-dispatch --action revoke --correlation EXACT_CORRELATION_FROM_STATUS --plan --json
```

The result contains the exact request digest, plan digest, authenticated actor, plan time, expiry, discovery counts, and apply command. Apply that command with an accountable reason. Apply re-verifies the immutable repository ID and actor, repeats the full paginated search, rejects a changed or expired plan, and records the decision in `integrated/audit.jsonl` before changing state.

Choose deliberately:

- `revoke` retires the ambiguous intent. The next `hive run` creates a fresh correlation. This is the preferred action whenever the original request might still reach GitHub or provider timing is uncertain; a late old run remains an identifiable orphan and cannot be consumed by the fresh correlation.
- `retry` preserves the correlation and authorizes one retry. Use it only when transport/provider evidence establishes that the original request was not accepted. Hive searches again immediately before the retry POST and requires the completed result to remain the sole exact match. GitHub's workflow-dispatch API has no atomic search-and-create or idempotency-key boundary, so an arbitrarily delayed original request can still race that final check; if two runs ever share the correlation, Hive rejects both and remains fail-closed.

Never delete `workflow-dispatch.json` manually, invent digests, or bypass plan/apply. If discovery errors, leave state intact and retry the read-only plan after GitHub recovers.

During first auto-merge activation, the dispatch checkpoint also spans the protection mutation. If Hive stops after the trusted run or receives an ambiguous protection response, rerun `hive run --json`: Hive reopens the exact run/head/job/Check Run binding, verifies live policy, and durably records activation without applying the evidence twice. If the default branch moved during that run, Hive discards only the exactly bound stale activation run and dispatches a fresh one on the next attempt.

If a generated repair or baseline branch collides with an existing remote ref, Hive will overwrite it only when the observed remote tip has the exact repository-ID/operation trailers and is an ancestor of the local checkpoint. Otherwise preserve the branch for investigation and choose an explicit recovery path; do not force-push it manually. A concurrent remote move is rejected by the exact SHA lease and can be retried after reviewing the new tip.

Every Hive merge has an audited exact-head/base/diff authorization snapshot and authenticated writer identity, so restart recovery can complete a Hive-initiated merge without accepting another actor's or an out-of-band direct merge. A stale approval is invalidated automatically; use `hive revoke-merge-approval --reason "..." --json` for an explicit withdrawal. If someone merged a held PR outside Hive, pause and investigate; Hive fails closed rather than silently clearing the hold.

## Upgrade and rollback

An upgrade or rollback PR changes the repository's immutable Visual Hive workflow pin. A hosted integrated-release transition additionally regenerates the managed repository configuration and controller workflow with the exact release tag, Hive commit, Visual Hive commit, and distribution-manifest digest. Install the candidate signed release and rerun the identical setup request so Hive records the currently installed hosted release as the one exact transition predecessor. Review and merge the one managed PR, then run:

```bash
hive run --json
hive doctor --json
```

The candidate controller may restore signed state only when it is already bound to the current release or to that explicitly recorded predecessor. Its next checkpoint is bound to the current release. Skipped releases, a different predecessor, mutable tags, workflow drift, or malformed release identity fail closed.

Do not treat reinstalling an older binary as rollback. After the current controller checkpoints a newer schema/release identity, an older binary is expected to reject it and preserve the state branch unchanged. Use the reviewable Hive rollback/setup path with a signed integrated release that understands the current schema and explicitly binds the current installation as its predecessor. If no such release exists, keep automation paused and publish a compatible immutable patch rather than editing state. Pixelmatch remains the default deterministic verdict engine; optional adapters cannot weaken this release/state boundary.

## Uninstall

### Merged setup with lost hosted state

If a hosted pod previously wrote repository state under ephemeral home storage, the managed setup PR can be merged while the replacement pod has no lifecycle state. Do not recreate state by hand and do not run setup again over the managed files. The authenticated dashboard reports `orphaned_setup.detected=true` only when the current default-branch head is one exact merged `hive/setup-<repository-id>` PR, every managed path still matches that reviewed setup head, and no later baseline, finding, or repair lifecycle exists.

Use the ordinary control plan/apply contract with operation `setup-reset`. Hive reconstructs only the exact pre-setup file bytes and Git modes from the immutable setup PR base, persists a bounded recovery receipt on `/data`, and delegates cleanup to its existing two-phase managed uninstall. It opens one reviewable `hive/uninstall-<repository-id>` PR. After that exact cleanup PR is reviewed and merged, plan/apply `setup-reset-finalize`. Finalization verifies the recorded PR/head/base/diff and exact restored tree, deletes only the temporary recovery state, and retires the prior hosted preflight receipt. Run a fresh hosted preflight before a new setup.

Recovery refuses a changed managed byte, a different current head, ambiguous setup history, committed baselines, post-setup Hive issues or repair/baseline PRs, wrong repository/actor identity, a moved cleanup ref, or an unreviewed merge. It never manufactures baseline approval, finding, or repair history.

`hive uninstall` is a durable two-phase operation. Preparation refuses ambiguous integrated recovery intents, then pauses automation and executes a bounded, audited cancellation drain. It closes only exact Hive-authored lifecycle issues, exact-marker repair/baseline PRs, and exact-head Hive branches; pending outbox work is cancelled and findings/repairs become terminal `cancelled` checkpoints without being represented as fixed. An ownership or ref mismatch leaves the installation paused and all evidence available for the same command to retry. Preparation then persists the exact cleanup PR identity/head/base/diff/path set and always returns with `finalization_pending=true` and local state preserved, even if `--delete-state` was supplied. After that exact PR merges, run the returned `next_command`. Finalization repeats quiescence, re-reads all recorded PR evidence, proves every managed file absent at one immutable current default-branch commit, and verifies protection reconciliation before deletion. Hive never deletes or rewrites an entire protection policy because GitHub has no conditional exact-context mutation immune to a concurrent administrator change. Remove only the exact `visual-hive` required context while preserving unrelated policy, then retry. Any mismatch fails closed and retains the config, audit, intent, lifecycle, repair, and activation evidence for recovery.

Before merge, `hive uninstall --cancel --json` (MCP `hive_uninstall` with `cancel: true`) is the supported stale-cleanup recovery path. It authenticates the recorded numeric setup authorizer, binds the exact repository ID, recorded PR number/URL, transaction marker, managed head/base branches, and unmerged state, while allowing only the base/head SHA drift caused by strict-base updates. It retires a moved cleanup ref only after proving the original Hive cleanup commit is its ancestor. Wrong marker, PR, URL, branch, repository, non-descendant head, ambiguity, or merged state fails closed. Cancellation is resumable after an interrupted close/delete, restores the pre-uninstall setup PR identity, leaves automation paused, and permits a fresh `hive uninstall` transaction without colliding with the closed PR.

Hosted uninstall has no local service to remove; it drains lifecycle state and uses the managed cleanup PR/state reconciliation described above. In explicit local mode on Linux, uninstall disables and removes only Hive's exact systemd user unit. It intentionally does not run `loginctl disable-linger`: linger is account-wide and may be required by unrelated user services. An administrator who knows the account has no remaining persistent user services may change that operating-system setting separately after reviewing the account.
